# M0 本地运行决策

日期：2026-11-14。范围：FND-050、FND-047、FND-048、ADR-002/014/015，以及 API-002～006、API-010 的可运行基础。

2026-11-14 后续修订：用户明确否定固定 Agent Workflow。产品入口改为单个自由 LangChain Agent，由 `.agents/skills/recommend-literature/SKILL.md` 提供行为指导，通过 `search_literature` 自主决定查询、改写、补查和停止。多库 Worker 并发与提交流程仅封装在工具内部；每次工具调用保留独立 query、排名、覆盖和快照。推荐理由由真实模型调用生成，不能使用关系标签拼接或固定文本冒充。密钥仅存于 Git 忽略的本地运行配置。使用有效密钥后，真实 DeepSeek Agent 已实际调用检索工具，4 条演示结果均由真实模型生成推荐理由；真实浏览器结果页及证据详情也已核对模型出处。这只验证模型与工具路径，不证明真实论文召回、关系核验或科学质量。

## 为什么适度变通

规格以 FastAPI + PostgreSQL 为部署基线。当前没有产品代码、数据库服务或真实检索结果；同时搭建 PostgreSQL、pgvector、Next.js 和对象存储会扩大排错面，不能证明用户最关心的流式与证据契约。

M0 使用 FastAPI + 本地 SQLite + 原生 HTML/JavaScript。两者是**可替换的本地适配器**，不是宣布永久替换规格中的 PostgreSQL/Next.js，也不冒充 PostgreSQL 的并发锁实现。M0.5/M1 再根据解析、检索与存储实测决定生产基线。

自由 Agent 采用用户明确要求的 LangChain 1.5.0 + langchain-openai 1.8.0（均为 MIT），OpenAI 3.51.0 客户端（Apache-2.0），模型与工具调用共享一个客户端边界。仅引入这些运行时依赖，不引入 Deep Agents、Tower 或多 Agent 框架；后续已增加独立认证 MCP 接口，见 README 的实际验收。维护风险是 LangChain 循环和模型兼容 API 的升级，因此 lockfile 固定版本、测试使用完整调用签名的可控模型，并保留传输独立的 `SearchService`。若未来更换模型提供方，只替换模型网关；不恢复固定 Agent Workflow。

## 本期交付

- 版本化请求/响应模型、身份与 UTF-8 字节证据校验。
- 本地持久搜索会话、Worker、Recommendation、outbox、Snapshot。
- 独立测试库 lane，确定性延迟，逐条结果提交；慢库不阻塞快库。
- SSE 持久事件重放、`Last-Event-ID`、保留窗口与一致状态读。
- drain 后固定 `finalize_cut`、证据包与内容寻址的不可变快照。
- 单个自由 LangChain Agent、项目 Skill、白名单 `search_literature` 工具和较大的防失控上限（当前 32 次；不是检索轮次质量门槛）。
- Agent 运行幂等、租户隔离、取消与持久化；自主多次检索时保留独立结果集，不混合排名。
- 真实模型推荐理由的调用与错误语义；模型未配置或认证失败时不伪造理由或 Agent 成功。
- 简单原生网页，真实访问 Agent 与检索 SSE；模拟文献明确标识，多查询仅在需要时显示切换。

## 明确非目标

- 不把本地 fixture 产生的书目、关系或分数说成真实科学结论。
- 不实现真实 PDF 阅读顺序保证、语义关系核验或概率校准；真实推荐理由也不等于真实关系核验。
- 不把 LangChain Agent 包装成另一套固定 Workflow；Tower / Agent Team 不属于运行依赖。
- 不把 SQLite 单写者实现宣称为分布式协调或高可用 Worker 队列。
- 不提供自动引用句或 DOCX 写回；认证网页与 MCP 公网访问属于后续已验收的有限候选发现能力，不代表全文或导出能力完成。
- 不以 M0 延迟作为生产 SLO。

## 2026-11-15 大库与索引决策记录

问题：493 篇快照不足以覆盖多学科试用；直接扩到 11,002 篇后，BM25 每次重新分词全库，稀疏查询中位约 2456 ms；JSON 向量还会增加解析与 Python 点积成本。

简单基线：保留既有 BM25、E5 small 与固定 RRF，不引入搜索引擎、LTR 或分布式服务。适配器初始化时复用 BM25 分词、长度与文档频率；E5 仍以相同 query/passage 前缀与归一化生成向量，仅以 NumPy NPZ 矩阵存储，并用矩阵乘法替代 Python 逐项点积。

证据：v3 的 21 个调参主题 Hit@5=21/21、nDCG@5=0.9446，三次排序一致；BM25 索引复用前后逐案候选、分数、顺序与指纹完全一致，中位耗时降至约 464 ms。新查询的混合检索中位约 1948 ms，缓存重复调用约 22.5 ms，二者不混合报告。

取舍与回退：NumPy 本是 fastembed 的传递依赖，现显式声明为直接运行时依赖（实际包元数据：BSD-3-Clause AND 0BSD AND MIT AND Zlib AND CC0-1.0），锁定文件记录实际版本。新增复杂度仅是本地索引与矩阵缓存，不改变科学评分规则；若一致性测试或性能收益失效，可回到每次构建稀疏索引，并恢复其他序列化缓存，不改变公共 API。大库首次本机嵌入峰值约 2.1 GB，超过生产内存上限，所以发布必须携带预建向量缓存，缺失即拒绝，不能让在线请求临时嵌入全库。

## 2026-11-15 在线库与双快照决策记录

问题：真实模式只注册一个本地适配器，却把数据来源写成 Europe PMC，导致用户无法区分在线数据库、11,002 篇多学科快照和老师提供的 50 篇样例；也无法实际补查快照之外的新论文。

简单基线：保留现有模块化单体和每库 Worker，不引入新的检索服务。`online.py` 用标准库 HTTPS 调用 Europe PMC 原生相关性 API，在有限 TopN 内复用现有题录候选契约与 BM25；大库继续使用既有混合索引，样例库使用相同稀疏适配器。`LibraryInfo` 增加来源类型与真实数量，前端直接消费，不建立第二份注册表。

证据与边界：真实请求已返回目标 DOI `10.1007/s42994-024-00192-2`；契约测试覆盖三路 Worker、来源合并、远程失败隔离和三方不可比状态。在线响应指纹不是远程全库不可变索引，TopN 不是全库最优。同步适配器经 `asyncio.to_thread` 执行并按适配器串行保护，避免阻塞事件循环；不为此新增任务队列。可通过 `CITATION_EUROPEPMC_ONLINE=0` 禁用在线来源，其余本地能力不变。


## 2026-11-16 评价锚点与分面召回决策记录

问题：同一论文在不同 Agent 改写下出现对齐分漂移；长查询中 DestVI 一度位于向量第 387 位；多对象比较中后续研究压过 2017 年目标。另有把其他试验的盲法/开放标签移植到当前论文的真实错误。

简单基线：保留单 Agent、BM25+E5/RRF、固定融合权重和模块化单体，不增加 LTR、规划 Agent、分布式队列或新模型服务。`EvaluationAnchor` 把原始研究需求与召回改写分开；理由输入增加年份、作者和版本身份。原始查询之外仅补充最多四个长度至少 24 字符的正向主题 facet，以平均 RRF 合并；候选池按 facet 数有界扩展。最终设计属性按句/段落绑定来源，一次纠正失败则明确失败，不输出模板理由。

证据：21 个既有调参主题保持 21/21 命中且三次候选、分数、顺序一致；年份探针将两篇 2017 目标恢复前二；DestVI 由第 387 位进入实际候选池，最终真实 Agent 回答正确。正常双盲得到保留，病理注释、否定和撤回不会误拦；跨试验“开放标签”会触发纠正。完整 Python 116 项、前端 22 项通过。首次 v3 独立评测产品 23/24、Kimi 24/24，整体未达发布条件；多对象局部领先不能掩盖该失败，v4 首轮独立对照另行验证。

取舍与回退：最多五次局部向量查询和更大的候选池会增加计算量；有限设计校验只覆盖随机化、开放标签和双盲，不保证所有科学事实正确，也可能需要更具体的来源表达。相同 Claim/候选/模型/版本使用租户隔离的真实理由缓存，不共享旧回答。若完整对照没有质量收益、正常证据被频繁误伤或既有检索退化，则回退到单查询召回与原评价方式；模型、提示、评分与缓存均带版本，不混用新旧结果。两轮 LTR 已因退化弃用，不为技术新颖性保留。

## 2026-11-16 来源自治与中央列表重排决策记录

问题：逐篇四档评价难以比较同档文献；各库只执行一次召回，不能自主发现缺失对象。用户明确批准每库首轮可靠召回后接 ReAct 子 Agent，再将候选归并、共同评分，最终由 LLM 决定顺序并解释。

简单基线：继续复用 LangChain `create_agent`、原适配器、BM25/E5、SQLite 和原生网页，不引入新 Agent 框架、搜索服务或生产依赖。来源子 Agent 只有本库搜索与显式提交工具，不能提供自造题录。中央池保留来源记录，不拼接摘要；共同基础分不依赖变化池的词频。LLM 不看基础分和名次，以完整排列与逐篇原文依据输出顺序。榜单按池版本原子提交、独立保存历史，不改变摘要候选的引用资格。

证据与未完成项：首批 10 个新架构契约测试通过；全套 Python 128 项、前端 26 项、真实 HTTP/SSE 冒烟及规格检查通过。旧版两案对照产品自动预期 1/2，新版同题 2/2，Kimi 两轮均 2/2；仅是开发证据，不证明普遍优势。三库真实浏览器试用随后暴露否定式缺口理由被实体闸门拒绝、网页附带演示 scope 与在线补查超时，均保留失败，不将两案成功当作试用已就绪。完整对照与修复闭环以 README 的实际记录为准。

后续实测：v5 完整开发对照双方完成/自动预期/科学硬门槛均 24/24，候选 nDCG 同为 0.9581；产品榜单仍仅 27/33 完成，不能当成全面试用通过。MCP 三来源真实验收通过，但网页大池出现完整 ID 复制错误；采用短窗口编号与严格映射后，本地 152 项 Python/28 项前端通过。v6 运行后段及评审因 DeepSeek 402 余额不足阻断，最新短编号真实验收仍待恢复额度；未部署生产。全部失败与原始报告保留在 README 指向的目录。

2026-11-16 断点续验：短编号版完整科学开发对照双方均 24/24，但 33 次查询榜单仅 32 次完成，且真实三库页面仍失败。通过保存的真实候选复现，定位到需求对比措辞触发实体闸门、模型 JSON 顶层多写 type 与临时编号进入理由。保留严格闸门，改为完整排列结构通过后仅恢复失败单篇理由，不再次生成整组顺序；结构纠错带上次输出及不含输入正文的字段路径/类型。报告显式披露开发证据、冻结 Kimi 复用与独立榜单完成率。新增六项回归后共 158 项 Python 通过；本轮真实修复版结果以 README 为准。

后续质量修复：来源实体规范化统一先合并已有格式空格、再折叠大小写，避免把 Fe2 O3、H2 O、C3 N4 误拦；未放宽实体白名单，也未改写原始证据。评审器补充真实全库元数据和双方实际提及的库内来源，修复真实治理说明被误判的问题；原始评审与全量重评分开保留。更充分评审又发现父 Agent 把未返回的 DOI 从记忆贴到错误排除项，故增加编号来源校验及 Skill 身份指导，不建立固定检索步骤；用户给定编号、真实更正关联与无需检索的回答均有回归。实际最新数字和是否完成真实验收以 README 为准。

取舍与回退：列表排序会引入输入顺序敏感性、长上下文和理由校验耦合；采用固定输入排列、租户缓存、重叠窗口及明确失败，不声称严格全局最优。保留 `CITATION_CANDIDATE_PIPELINE=pointwise` 作为旧版机制对照。来源自治与中央重排必须用真实模型和完整失败计入评测；质量退化先归因，不能改金标或默默回退掩盖。重排机制借鉴 [RankLLM](https://arxiv.org/html/2505.19284)，来源隔离参考 [LangChain subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)，不是宣称这些通用方案已证明本产品优效。
