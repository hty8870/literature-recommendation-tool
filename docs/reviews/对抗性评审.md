# 文献推荐工具_对抗性评审

> 评审对象：`文献推荐工具_AGENT_SPEC.md` v1.1.0（1704 行）、`AGENTS.md`（410 行）、设计文档 V1.0，以及 5 份独立评审报告。
> 评审日期：2026-11-14。
> 性质：只读评审与提案；**未修改任何现有 SPEC/AGENTS/DOCX**；**未运行代码、测试或基准**。仓库尚无源码与命令表。
> 结论边界：本文不声称任何方案全局最优；所有“更优”都是指定指标、数据和约束下的条件判断。

## 0. 结论

1. 规格的“正确性骨架”是对的：逐字证据、`insufficient` 拒答、快照不可变、事件幂等、编号只在导出侧生成。这些不应为了性能或便利削弱。
2. 但 `status: implementation_ready` 目前不成立。问题不是代码 bug（尚无实现），而是**设计阻断项**：身份模型、协调器边界、事件语义、评分语义、技术基座和验收口径尚未闭合。建议先改为 `revision_required`，关闭 AR-01/02/04/06/07/08 后再评估。
3. 推荐路线不是推翻重来，而是“保留不变量、重构执行骨架”：canonical work / source / claim 三层身份；逻辑每库 lane + 共享公平模型池；协调器纯提交；单 query sequencer/outbox/watermark；快照 manifest + 证据包；导出闸门；有界规划器，Agent 是否首轮由基准决定。
4. 最容易被“测试通过”掩盖的三个问题：`AT-STR-001` 只阻塞 Worker B，不阻塞共享重排池；`AT-SCR-001` 只测同输入同分，不测跨查询/跨来源分布；`AT-DED-001` 只测同 DOI 合并，不测同一论文跨多条 claim。测试通过不等于承诺成立。
5. 不声称“全局最优”。当前证据只支持“某些结构更符合约束”，不支持“某个平台/模型/阈值一定更好”。所有默认值必须由本项目基准和标注集校准。

## 1. 为什么 `implementation_ready` 标签不成立

SPEC 第 4 行确实写着 `status: implementation_ready`。按“可执行、可测试、可追踪”的定义，至少五处不满足：

| 缺口 | 事实 | 后果 |
|---|---|---|
| 技术选型缺失 | 只有目录树与框架名（FastAPI/Next.js/Postgres），没有版本、引擎、解析器、队列、认证选型；AGENTS 引用的“AGENT_SPEC 选型章节”不存在 | T01 难以锁依赖；实现者容易各自选 `ts_rank`/ParadeDB/OpenSearch，形成三套分数口径 |
| 契约自相矛盾 | AGENTS 要求同分比较“证据完整度与适用性”，SPEC `RANK-002` 只按 `(display_score, result_id)`；`sequence` 要求步长 1，但数据库序列非事务性；`finalizing` 是布尔状态，不是水位 | 可能导致排序/快照哈希分叉、SSE 永久丢事件、快照标称完整却漏推荐 |
| 身份模型不闭合 | `result_id=doi:...`，`Recommendation.paper` 只能指向一个 `paper_id`，`claim_id`/`relationship` 各只有一个，`evidence[]` 却是数组 | 同一论文对多条 claim 的关系被压扁；跨库证据无法与主 Paper 对齐 |
| 验收不可判定 | 无绝对 SLO；`global_max=120` 未说明是“每 query”还是“每 claim”；假模型只能证明契约，不能证明“该不该引用”；DOD-004 把统计问题写成“零” | M1/M2 可能“全绿”但产品不可用；成本/召回解释相差数量级 |
| 启动死锁 | AGENTS §11.3 命令表为空，§11.1 只允许仓库已有命令，§6.2 要求所有需求测试在默认集运行；§7.2 要求新增依赖先证明现有依赖不足，但 greenfield 没有“现有依赖” | 第一个提交无法同时满足“有命令/有测试/依赖批准” |

**判定**：这不是“规格不够详细”，而是“详细到了不可执行、不可证伪”。`implementation_ready` 应改为 `revision_required`，并附本文 AR 清单；在 AR-01/02/04/06/07/08 关闭前，不应把 M0 称为“骨架可启动”。

## 2. 推荐架构

```text
Browser
  │ POST /searches, GET /events (fetch-based SSE)
  ▼
API / Query Service
  │ QueryBundle 一次：normalized query + expansions + embeddings + filters + versions
  ├─ Lane A (library A): recall → RRF → candidate descriptors ─┐
  ├─ Lane B (library B): ...                                   ├─ 逻辑每库隔离
  └─ Lane C: ...                                               ┘
                     ▼
         Candidate Registry（work/source/claim 身份 + 单飞租约）
                     ▼
         Shared Rerank / Verification Pool（per-library WFQ/DRR + EDF，廉价门控 → LLM）
                     ▼
         Coordinator（只做校验、幂等、去重、分数版本检查、有序插入、outbox；禁止同步模型调用）
                     ▼
         SSE Projector / GET state（as_of_sequence）
                     ▼
         Snapshot manifest + evidence bundle → Export/Citation（独立生命周期 + 导出闸门）
```

这套结构不是本项目的发明：RRF、Elasticsearch async search 的部分结果、Vespa 的分阶段排序、transactional outbox、Flink watermark、manifest/WORM、CSL/citeproc、OWASP LLM01/CaMeL 都是成熟做法。本项目的差异化不在重写这些算法，而在把 claim 级证据、覆盖诚实和导出资格接进这些机制。

六个原则：

1. **身份分三层**：`work`（知识对象，DOI/OpenAlex/Crossref 解析）→ `source_record`（库内 `paper_id`、元数据、许可）→ `claim_link`（论文 × claim 的关系、证据、分数、引文句）。`result_id` 在全文/摘要模式按 claim 生成；关键词模式可为 work 级、`claim_id=null`。DOI 仍用于 work 去重，但不再单独决定推荐身份。
2. **逻辑每库、物理共享**：保留每库 lane、attempt、coverage 和失败隔离；只把重排/核验放进共享池，按库公平调度、按 query 配额、按 deadline 准入。共享池不是“合并 Worker”，不改变覆盖语义。
3. **协调器只提交**：权威是提交权，不是计算位置。模型调用必须在事务外、协调器外完成；协调器 trace 中不得出现 `model_call` 子 span。
4. **每 query 单写者**：`sequence` 由 per-query sequencer 在事务内分配并与状态同事务提交，禁用 `nextval`/`IDENTITY` 作为公开序号；outbox 按 `query_id` 分区，单消费者。
5. **快照是 manifest，不是大 JSON**：快照只存有序 `SnapshotItem` + 覆盖/版本/水位/哈希；证据包内容寻址、可独立复验；导出闸门读当前撤稿/授权/删除状态。
6. **Agent 是可选规划器，不是首轮必经**：默认用规范化查询立即派发；有界规划器并行补充；Agent 仅在复杂/歧义查询中触发。模型工具（规划、核验、写作）有 Schema、权限域和预算，不等于自治 Agent。M0/M1 用模块化单体（FastAPI + Postgres + pgvector + 词法索引 + 进程内 lane），不要先拆四个服务。

### 3.1 必须先钉死的四个契约

**AR-01（身份）**：这是最贵、也最不能拖的一项。只要 `result_id` 仍按 DOI 合并，全文模式的跨 claim 场景就必然出现“先到 claim 获胜”。推荐 `work_id` + `source_record` + `claim_link`；`Recommendation` 保留论文级容器用于分组，但排序、引用句、导出和插入位置消费 `claim_link`。证据按 `claim_link` 绑定：同一 `(work_id, claim_id)` 内可合并，跨 claim 只共享 work 级来源，不共享证据。若产品坚持论文级卡片，至少加 `claim_bindings[]`，不能让论文级 `relationship` 覆盖冲突。

**AR-04（分数）**：先定义“分数预测什么”，再谈校准。建议 0–3 级 rubric：不引用 / 背景 / 可引用 / 应引用；所有 calibrator 预测同一目标（如 `P(grade≥2)`），并记录 rubric 版本。`score_scale_group` 表示“同一 scorer fingerprint + 同一输入/聚合规则下可排序”；`probability_calibration` 表示“是否有足够标签解释为概率”。`bootstrap` 只能在组内排序，不得与 `source_calibrated` 混排；`citable` 与 `rankable` 分开，已核验但不可校准的结果进入独立分组，仍可导出但带警告。评分只用 verified 证据；新增证据不得让分数下降（用 max 或确定性 top-k 聚合，而非并集拼接）。

**AR-06（事件）**：`sequence` 不是数据库序列，而是 per-query 单写者的提交序号。`finalizing` 必须变成 `finalize_cut = applied_through_sequence`；先停止接收新事件，drain 已接受事件（短事务），再写快照。`worker_completed` 必须晚于该 attempt 的所有推荐事件，并携带 `last_emitted_sequence`/`emitted_event_count`。`GET state` 在 `REPEATABLE READ` 中同时读 results/workers/`as_of_sequence`；客户端从 `as_of_sequence` 续传。`WorkerStatus` 主键加 `attempt`，否则重试会覆盖终态。

**AR-08（快照/生命周期）**：快照内容不变，但“可核查”不能依赖活库。证据包至少含 `quote`、`quote_sha256`、`raw_text_sha256`、偏移、页码/bbox、`parser_version`、`normalization_version`、`source_resolver_id`；`immutable_hash` 用 RFC 8785 JCS，并记录 `hash_alg`/`canonicalization`。撤稿/授权撤销/稿件删除用**追加注解 + 导出闸门 + 密钥销毁**处理：不改快照字节，导出时读当前 `PaperStatus`/entitlement/manuscript 状态，阻断或显式警告，并记录 `notice_version`/`status_checked_at`。

### 3.2 其余问题的一句话判断

- **AR-02**：把 `SCR-004` 的“协调器”改为“无状态评分服务”；协调器事务只写状态 + outbox。没有这一步，AR-06 的单写者会被模型延迟拖死。
- **AR-03**：不要默认上共享池。先用实验证明 FIFO 下轻库 TTFF 被重库拖慢；若只有 1–2 个库、低 QPS，per-library + 全局 token bucket 更简单。
- **AR-05**：`source_trace_valid=true` 目前只说明“我们的解析器在自己的输出里自洽”。双栏、断词、OCR 都可能字节一致但原文错误；必须拆谓词并把 OCR/阅读顺序质量带入门槛。aBiotech 场景尤其要加 `scope_match`：拟南芥温室结果不能直接 `support` 大豆田间 claim。
- **AR-07**：搜索流关闭后，导出/引文句是独立资源。`GET /exports/{id}` 是权威，SSE 只是加速器；引文句用带 `result_version` 的读接口，导出不调用 LLM。
- **AR-09**：PostgreSQL 官方文档明确 `ts_rank`/`ts_rank_cd` “不使用任何全局信息”，所以它不是 BM25；若要 BM25，选 ParadeDB `pg_search`、VectorChord-BM25 或 OpenSearch/Elasticsearch，并用同一语料基准比较。平台选择（Postgres vs OpenSearch/Vespa）必须由召回/延迟/运维基准决定，不能由“功能看起来更强”决定。
- **AR-10**：Agent 的增量价值主要是查询扩展和停止判断，不是逐篇扫描。默认立即派发 + 有界规划器；Agent 只在复杂查询中追加。能力分离可在单进程内用不同工具域实现：Planner 不读原文、Verifier 无工具、Writer 无工具、Export/Delete 需用户确认令牌。AGENTS 应缩到约束与 ID 引用，删除重复需求正文。

## 4. 三类行动

### A. 立即修正（M0 前，规格/契约层）

1. **AR-01**：冻结 work/source/claim 三层身份；明确 `result_id` 生成规则与迁移方式。
2. **AR-02**：写入“协调器禁止同步模型调用”的实现约束；补 trace 断言。
3. **AR-06**：补 per-query sequencer、`applied_through_sequence`、`as_of_sequence`、`attempt` 键、retention/backpressure。
4. **AR-07**：把导出/引文句改为独立资源状态机；删除搜索流上的 `export_ready` 依赖。
5. **AR-05**：补证据三谓词、`scope_match`、`evidence_role`、span 选择接口。
6. **AR-08**：补证据包 schema、JCS、导出闸门、append-only 注解、删除回执。
7. **AR-10**：修 tie-breaker 冲突；AGENTS 增加 T01 bootstrap 例外、baseline 依赖预批准、报告分档；把“选型章节”改为真实 ADR 路径。

### B. 需决策（用户/主控批准，不能由实现 Agent 自定）

| 决策 | 选项 | 代价 |
|---|---|---|
| AR-01 身份 | claim-scoped `result_id` vs 论文级 + `claim_bindings[]` | 前者结果行多、UI 分组；后者迁移小但排序/引用仍需按 binding |
| AR-03 执行 | 共享公平池 vs per-library + 全局限流 | 前者 TTFF/吞吐更好但调度复杂；后者简单但重库可能拖慢轻库 |
| AR-04 分数 | `citation_utility` vs `topical_relevance`；是否拆分 citable/rankable | 前者更贴产品但标注贵；后者便宜但可能“相关却无用” |
| AR-08 生命周期 | 快照不可变 + 注解/导出闸门 + crypto-shredding | 合规/诚信更好，但 KMS/导出闸门复杂 |
| AR-10 Agent | 单 Agent + 权限域 vs 确定性 Planner + 可选 Agent | 前者保留产品叙事；后者更快/可复现但灵活性下降 |
| AR-09 引擎/预算 | Postgres FTS / pg_search / OpenSearch / Vespa；成本上限 | 需基准与预算，不能凭偏好 |

### C. 需实验（基准前不得锁默认值）

| 实验 | 问题 | 通过标准（建议，非已达成） |
|---|---|---|
| EXP-IDENTITY | 同一论文对多条 claim 的 6 种到达顺序 | claim 身份、anchor、evidence 集合与顺序无关；0 跨 claim 证据混入 |
| EXP-FAIR | FIFO vs WFQ/EDF；重库/轻库 | 轻库 TTFF p95 不因重库线性增长；无饥饿；吞吐损失可接受 |
| EXP-CAPACITY | 120 候选、8/16 并发、核验 p95 2/5/8s | 90s 内完成或显式 `is_partial`；不静默零结果 |
| EXP-SCORE | 同模型跨库/跨 query 分布；bootstrap vs 校准 | 控制标签后库身份不应解释分数；等价性检验通过才可混排 |
| EXP-EVIDENCE | 50 篇 PDF 双栏/断词/OCR/表格 | 视觉复核通过率达标；跨栏拼接 0；OCR 不直接进可引用集合 |
| EXP-INJECT | 标题/摘要/证据/稿件中的注入 payload | 工具调用序列与无注入一致；0 越权/0 跨租户/0 泄露 |
| EXP-AGENT | 有界规划器 vs Agent 首轮 | 召回不劣（或差异可接受）；TTFF 更快；成本可解释 |
| EXP-PLATFORM | Postgres vs OpenSearch/Vespa | 在目标语料/查询集上比较 Recall@K、p95、运维成本；不预设赢家 |
| EXP-GOLD | 200–300 条 claim-paper-evidence-relationship 标注 | 双人标注 + 仲裁；κ 达标；报告 CI 和样本量 |

## 5. 权衡与 Pareto 评估矩阵

**硬约束（先淘汰，不参与加权）**：证据可核查；无依据不生成引用句；租户/稿件隔离；快照不被后续事件修改；首结果路径无全局屏障；已撤稿论文不进入可引用集合。

**候选配置**（C0 为字面规格；C1 为契约修正后的基线；其余为增量）：

| 维度 | C0 字面 | C1 契约修正 | C2 +共享公平池 | C3 +原生平台 | C4 +claim 两级评分 | C5 +可选 Agent | C6 +证据优先分组 |
|---|---|---|---|---|---|---|---|
| 质量/证据正确 | 中 | 高 | 高 | 高 | 高+ | 高 | 高 |
| 召回 | 中 | 中高 | 中高 | 中高 | 高 | 高 | 中高 |
| 首结果 TTFF | 中 | 高 | 高+ | 高 | 中高 | 高 | 高 |
| 最终延迟 | 中 | 中高 | 中高 | 中高 | 中（二级可选） | 中高 | 中高 |
| 吞吐 | 中 | 中 | 高 | 高 | 中高 | 中高 | 中 |
| 成本 | 中高 | 中 | 中 | 中高 | 中低（LLM 只处理 Top-M） | 中 | 中 |
| 复杂度 | 中 | 中高 | 高 | 高 | 高 | 中高 | 低中 |
| 安全/合规 | 中 | 高 | 高 | 高 | 高 | 高 | 高 |
| 可实施性 | 低（歧义） | 中高 | 中 | 中低 | 中 | 中高 | 高 |

> 符号为方向性判断，不是实测；C1 是所有后续配置的前置，不与 C2–C6 直接比较。

**Pareto 判断**：

- C1 是“必要不充分”：没有它，C2–C6 的比较没有意义。
- C2 与 C3 都改善 TTFF/吞吐，但代价不同：C2 是调度复杂度，C3 是平台运维/许可/迁移。二者可能互不支配，按团队能力选。
- C4 改善质量与 claim 覆盖，代价是 Schema/UI/核验调用；若没有 claim 级 qrels，不应默认开启二级 listwise。
- C5 改善复杂查询召回，代价是延迟/成本/不确定性；若基准显示 Agent 首轮召回提升不显著，默认关闭。
- C6 降低校准负担和“分数=概率”误读，但失去单一全局排序；建议作为可选视图，不替代主排序，除非用户研究支持。

**实测纪律**：同一 query 集、同一金标、同一模型/硬件版本；配对 bootstrap + 95% CI；报告 p50/p95/p99；失败/超时计入分母；成本算全口径（token、rerank、embedding、索引摊销、存储、运维）；只报告“已评估配置中的非支配集”，不写“全局最优”。
