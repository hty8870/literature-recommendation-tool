## 0. Agent 使用方式与规范语言

### 0.1 文档作用

本规格是编码 Agent 的实施基线，目标是将“证据驱动的多库流式引用推荐系统”转化为可运行、可测试的软件。原《文献推荐工具_设计文档.docx》仅作背景说明；实施时以本规格中的 MUST、数据契约和验收测试为准。

**FND-001｜规范语言**：文中 **MUST** 表示验收必需，**MUST NOT** 表示禁止，**SHOULD** 表示默认实现、仅有证据证明更优方案时才可偏离，**MAY** 表示可选优化。示例 JSON、目录名和开发默认值用于消除实现歧义；若示例与 MUST 条文冲突，以 MUST 条文为准。

**FND-002｜冲突优先级**：实现或优化发生冲突时， MUST 按以下顺序取舍，低优先级优化不得破坏高优先级约束：

1. 文献、原文、证据、隐私和安全真实可靠；
2. 证据核验、引文、去重和快照一致性；
3. 候选召回、跨库排序正确性和覆盖真实性；
4. 首条有效结果延迟、吞吐和交互流畅度；
5. 模型成本、界面动效和其他体验优化。

**FND-003｜已冻结决策**：编码 Agent MUST NOT 为方便实现而重写第 2 章 ADR。确需变更时，必须记录变更原因、影响范围、回退方案和验证证据，并取得用户明确确认；不得将变更静默混入代码。

**FND-004｜实施证据**：每个实现任务 MUST 同时交付代码、覆盖其需求的测试、实际执行过的验证命令及结果。未执行的检查 MUST 标记为“未运行”，不得写成“已通过”。测试替身只能用于隔离测试，不得将模拟检索、模拟证据或模拟模型输出描述为真实端到端能力。

**FND-005｜外部副作用**：本地代码、测试和 Docker 验证可在任务授权内完成。生产部署、创建计费云资源、向外部数据库写入生产数据、公开私有稿件或修改线上服务 MUST 另行取得用户明确授权；实施规格本身不构成部署授权。

**FND-006｜偏差与阻塞**：无法遵守 MUST 时，Agent MUST 停止依赖该偏差的后续工作，保留已通过的检查，并报告阻塞点、已尝试路径和受影响需求。不得通过删除测试、降低断言、吞掉异常、硬编码演示结果或缩小验收范围制造完成状态。

### 0.2 实施输入与任务输出

实施输入包括本规格、原始需求文档、50 份测试 PDF，以及后续明确提供的模型和云服务配置。每个任务的标准输出为：

- 可审查的源代码和必要配置；
- 与需求 ID 对应的自动化测试；
- 数据库迁移或索引迁移（若涉及）；
- 实际验证结果和仍未覆盖的边界；
- 偏离 SHOULD 或开发默认值时的理由与证据。

## 1. 产品目标与非目标

### 1.1 产品目标

系统根据关键词、摘要或论文全文，在合作期刊论文库中寻找具有实际引用价值的文献，并提供可核查原文、推荐理由、引用位置、可编辑引用表述和规范引文。系统面向云端浏览器使用，采用异步任务支持长时间全文分析。

**FND-010｜证据驱动**：系统 MUST 将候选相关性、原文证据和引文格式分开处理。相似度不得直接转换为“应该引用”的结论；没有有效原文依据时不得生成可直接粘贴的引用句。

**FND-011｜用户控制**：用户 MUST 能查看证据、忽略或选择推荐，并主动创建结果快照和导出。系统不得在用户不知情时自动向稿件强插引用。

**FND-012｜覆盖诚实**：每次搜索 MUST 能表达各库运行、完成、失败、超时和未覆盖状态。部分结果不得伪装成全库完整结果，早期高分不得表述为最终胜出保证。

**FND-013｜真实可追溯**：论文身份、DOI、来源原文、页码、评分版本、结果版本和导出快照 MUST 可追溯。模型不得补写不存在的论文、DOI、原文或页码。

### 1.2 非目标与禁止退化

**FND-020｜非强制引用**：产品不以增加弱相关引用为目标，不承诺短期引用率提升，不提供“为了提高本刊引用量而绕过证据核验”的隐藏模式。

**FND-021｜非可视化工作流项目**：首期不实现固定 Workflow 画布。Skill 引导 LangChain Agent 的查询规划、补充检索和停止判断；确定性程序负责解析、检索、核验辅助、评分、去重、快照和引文处理。

**FND-022｜非运行时多 Agent 前提**：Tower / Agent Team 只可用于研发协作，不属于云端运行依赖。运行时首期使用单 Agent 加并行 Worker；不得要求每个库都部署自治 Agent，也不得将多 Agent 数量当作验收目标。

**FND-023｜非全库模型扫描**：不得让 LLM 在在线请求中逐篇阅读大型论文库。候选 MUST 来自离线索引和有限 TopN 漏斗，模型只处理查询规划及少量候选。

**FND-024｜非分散引文决策**：各库 Worker 不得独立生成全局最终排名或数字引文编号。跨库去重、快照和最终编号 MUST 使用全局一致状态。

### 1.3 可验证条件

- 产品测试能从三种输入进入同一推荐契约，同时保留输入模式差异。
- 任一可粘贴引用句都能追溯到证据通过的推荐和有效原文位置。
- 任一导出的数字标号都能在同一快照内对应唯一文末条目。
- 停止部分 Worker 后，界面和快照明确显示实际覆盖，而非伪装完整成功。

## 2. 已冻结架构决策记录（ADR）

以下 ADR 是跨模块共同约束。表中“实现检查”是最低验证要求，不替代后续章节的详细测试。

| ADR | 冻结决策 | 实现检查 |
|---|---|---|
| ADR-001 | 采用云端 Web、API、异步任务和独立 Worker；私有稿件与公共文献库隔离。 | 搜索可异步执行；权限测试不能跨用户或租户读取稿件。 |
| ADR-002 | 首期运行时为 LangChain 单 Agent + Citation Skill + 确定性工具服务。 | Agent 可选择工具和补充查询；页码、DOI、评分、去重和引文不依赖自由文本自觉。 |
| ADR-003 | 每库独立 Worker，处理到证据核验通过后逐条或小批发送；任何全局步骤 MUST NOT 等待全部库完成才开始。 | 用可控测试闩锁阻塞库 B，库 A 的有效事件和前端展示仍先发生。 |
| ADR-004 | 自控库统一解析后契约、分块、字段、向量模型、重排器和评分版本；外部异构库通过适配器接入。 | 同版本自控 Worker 使用同一配置；外部库不假装具有相同原始分口径。 |
| ADR-005 | 使用论文级与段落级两级索引，以及关键词与向量混合召回。 | 精确罕见术语和改写查询均有测试；两路结果取并集而非交集。 |
| ADR-006 | 候选预算采用动态 TopN、最低/最高数量、质量门槛和少量探索配额，不直接采用固定 k%。 | 大库不会仅因篇数多而线性扩大后续预算；低权重库仍有受控探索机会。 |
| ADR-007 | 展示分区分原始检索分和证据状态；同口径直接展示共同分，异构优先统一重排，无法统一时按来源校准。 | 分数绑定版本和校准状态；禁止用当前在线批次 min-max 作为长期跨库分。 |
| ADR-008 | 协调器对到达事件即时执行幂等接收、增量去重、统一评分和有序插入，不设置集中到期后的重排屏障。 | 迟到高分可插入当前列表；重复论文合并来源和证据而非简单丢弃。 |
| ADR-009 | 只有 support、complement、contrast 且来源定位有效的推荐可进入可引用集合；insufficient 不生成引用句。 | 原文定位失败或关系不足时，生成工具拒绝输出可粘贴表述。 |
| ADR-010 | 实时列表可变化；快照不可变。数字引文只在用户选择或导出快照时全局统一编号。 | 快照后事件形成补充版本，原快照及导出文件哈希和内容保持不变。 |
| ADR-011 | Tower / Agent Team 是研发方式，不是运行时架构；多 Agent 只在独立评估证明收益后引入。 | 本地和云端运行不依赖 Tower 状态、研发工作树或 Agent Team 会话。 |
| ADR-012 | 模块之间使用版本化结构化契约，不使用需要解析自然语言的隐式接口。 | 契约错误在边界返回明确错误，不产生半有效推荐事件。 |

## 3. 迭代范围与交付门禁

### 3.1 里程碑通用规则

**FND-030｜按门禁推进**：里程碑 MUST 按 M0 → M1 → M2 → M3 → M4 的依赖顺序验收。后续工作可以预先建立不破坏契约的骨架，但不得用后续界面或演示掩盖前一里程碑未通过的 MUST。

**FND-031｜不得静默缩小交付**：若环境只支持部分里程碑，Agent MUST 完成未受阻部分并明确剩余范围。是否接受缩小结果由用户决定，不能自行将“仅单库”“仅批处理”或“仅返回相似论文”改名为完整系统。

**FND-032｜回归要求**：每个里程碑 MUST 保留此前里程碑的测试。新功能导致旧测试失败时，先修复回归；不得通过删除旧场景获得绿色结果。

### 3.2 M0—M4 交付边界

| 里程碑 / 需求 ID | 输入 | 必须交付 | 完成判据 |
|---|---|---|---|
| M0 / FND-050 | 本规格、测试 PDF 清单、本地开发环境。 | 仓库骨架、版本化契约、配置校验、API/Worker/Web 可启动骨架、可控测试库与事件测试夹具、基础 CI。 | 健康检查和契约测试通过；非法配置快速失败；测试可独立控制 Worker 完成顺序。M0 的模型替身不得被描述为真实推荐能力。 |
| M1 / FND-051 | M0、50 份测试 PDF、单库模型配置。 | 单库真实入库、关键词与摘要输入、两级混合检索、原文证据卡片、基础统一分、无依据拒答、RIS/BibTeX 或复制输出。 | 使用真实 50 篇语料完成端到端；推荐可追溯至 DOI、原文和页码；弱相关和更正声明策略有测试。 |
| M2 / FND-052 | M1、至少两个逻辑隔离且可独立延迟的测试库。 | 并行 Worker、动态 TopN、SSE、统一/校准评分、增量去重与插入、Worker 覆盖状态、实时列表和不可变快照。 | 慢库不阻塞快库；迟到高分正确插入；跨库同 DOI 不重复；事件重放幂等；超时形成明确部分覆盖快照。 |
| M3 / FND-053 | M2、含章节和已有参考文献的全文样本。 | 全文位置、已有引用识别、证据约束的引用句、作者—年份和数字引文、编号联动、快照导出及变更清单。 | 已引用条目不重复；插入已有编号前后均一致；快照内正文标号与文末条目一一对应；无证据不生成引用句。 |
| M4 / FND-054 | M3、目标云环境的非秘密配置和经授权的测试资源。 | 租户与权限、对象存储、增量入库、部署模板、可观测性、安全/负载/恢复测试、评估报告和运维开关。 | 安全、并发、断线重连、Worker 故障和恢复场景通过；部署包可审查。实际生产部署仍需单独授权和线上核验。 |

### 3.3 里程碑失败行为

- M0 契约未稳定时，不得让多个模块各自复制并修改字段定义来继续推进。
- M1 证据定位不可靠时，不得进入自动生成引用句的验收。
- M2 的流式或快照一致性未通过时，不得仅用界面轮询截图声称多库完成。
- M3 的编号联动未通过时，只能输出不带最终数字编号的建议，不得导出貌似完整的数字引文稿。
- M4 未获云资源或部署授权时，只交付本地可验证的部署配置和检查报告，不创建外部资源。

## 4. 模块边界与推荐仓库结构

### 4.1 推荐仓库结构

```text
文献推荐工具/
├─ apps/
│  ├─ web/                     # Next.js / React 浏览器应用
│  └─ api/                     # FastAPI、REST、SSE、鉴权和搜索会话
├─ services/
│  ├─ coordinator/             # 预算、增量去重、统一评分、排序、快照
│  ├─ worker/                  # 每库检索、重排、证据读取和关系核验
│  ├─ indexer/                 # PDF 入库、解析、两级索引和增量更新
│  └─ citation/                # CSL、已有引用、编号联动和导出
├─ packages/
│  ├─ contracts/               # JSON Schema、枚举、错误和版本；唯一契约源
│  ├─ skill/                   # SKILL.md、工具说明和行为规则，不存秘密
│  ├─ library_adapters/        # 自控库与外部库适配接口
│  └─ config/                  # 环境配置、默认值和启动校验
├─ tests/
│  ├─ unit/
│  ├─ integration/
│  ├─ streaming/
│  ├─ eval/
│  └─ fixtures/                # 小型可公开测试夹具，不复制私有全文
├─ infra/
│  ├─ local/                   # 本地 Docker 编排
│  └─ deployment/              # 默认不自动执行的部署模板
└─ pyproject.toml / package.json / pnpm-workspace.yaml
```

实现 MAY 调整物理目录，但 MUST 保持下列依赖与权属，不得为了目录整齐合并相互独立的生命周期。

### 4.2 依赖方向与权属

**FND-040｜单向依赖**：`contracts` MUST 不依赖应用或服务；`skill` 只依赖契约和工具接口；Worker 依赖契约和库适配器；Coordinator 不依赖 Web；API 调用 Coordinator；Citation 只消费合法推荐和快照。禁止 Web ↔ API ↔ Coordinator 循环依赖。

**FND-041｜唯一契约源**：`packages/contracts` MUST 是枚举、事件、错误和版本的唯一定义源。Python 与 TypeScript 类型 SHOULD 从 JSON Schema 生成；若手写类型，必须有契约一致性测试，禁止各模块独立漂移。

**FND-042｜全局结果权属**：Coordinator MUST 是 `display_score`、全局 `result_id`、跨库去重、当前排序、覆盖状态和快照的唯一权威。Worker 可计算共同重排器输出，但不得自行决定全局排序或修改已固化快照。

**FND-043｜Worker 边界**：Worker 只访问被分配的库及模型工具，输出结构化候选、证据和核验结果。Worker MUST NOT 读取其他库的全局结果来“帮助”排序，不得直接操作全局快照或最终数字编号。

**FND-044｜Citation 边界**：Citation 服务 MUST 以不可变快照、用户选择和真实书目元数据为输入。它不得重新检索、改变证据关系或根据语言模型猜测缺失书目。

**FND-045｜前端边界**：Web  MUST 展示服务端计算的分数、排序、状态和版本，不自行发明跨库转换公式。前端可用稳定排序视图优化交互，但不得改变服务端权威结果。

**FND-046｜基础设施边界**：`infra/deployment` 的模板 MUST 默认不可自动执行生产变更；本地测试配置与生产秘密分离，仓库不得保存云密钥、私有全文或持久化用户稿件。

### 4.3 跨模块接口点

| 接口点 | 提供方 → 消费方 | 权属与失败行为 |
|---|---|---|
| 搜索会话 | API → Coordinator | API 创建 `query_id` 并校验输入；非法输入在启动 Worker 前拒绝。 |
| 库任务与预算 | Coordinator → Worker | Coordinator 分配库、查询、TopN、截止和取消条件；Worker 对不兼容版本快速失败。 |
| 证据推荐事件 | Worker → Coordinator | Worker 提供本地检索信息、可选共同重排输出、证据和核验状态；契约无效事件不得进入结果表。 |
| 全局评分与排序 | Coordinator → API / Web | Coordinator 返回统一展示分、版本、暂定状态和稳定顺序；评分不可比时明确标记而非隐藏。 |
| 状态与进度 | Coordinator → API / Web | Coordinator 聚合 Worker 状态；部分失败保留有效结果并显式显示覆盖缺口。 |
| 快照 | Coordinator → Citation / Export | 快照包含结果、证据、分数、覆盖和版本；生成后不得原地修改。 |
| 引文与导出 | Citation → API / Web | Citation 对快照和用户选择统一格式化；元数据不足时返回可诊断错误，不编造内容。 |
| 评估钩子 | 各服务 → Eval | 保留候选召回、证据通过、评分版本、事件时序和首条有效结果时间，不记录不必要的私有全文。 |

### 4.4 模块级验证条件

- 停用任一外部库适配器，不影响其他库 Worker 的契约测试。
- 使用两个不同版本的评分配置时，Coordinator 能拒绝无说明混排或执行明确的版本转换。
- 在 Worker 尚未返回任何结果时，Citation 不得虚构可导出的推荐。
- 事件重复投递、乱序到达和 Worker 超时均由 Coordinator 处理，Web 不需要通过猜测修复状态。
- 仓库中不存在“前端计算一个分、Worker 展示另一个分、快照保存第三个分”的三套权威逻辑。
