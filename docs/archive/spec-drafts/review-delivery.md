## 0. 执行摘要

这套规格的强项是证据、快照、幂等、覆盖诚实；弱项是把“正确性”写成了**不可执行的复杂度**，把“性能”写成了**相对判据**，把“完成”写成了**范围映射**。最严重的不是某条实现细节，而是五个结构性缺口：

1. **跨库合并后的数据模型自相矛盾**：`Recommendation.paper` 只能指向一个 `paper_id`，但 DED-004 要求合并多库来源与证据；来自另一库的 `Evidence.paper_id` 无法与主 `Paper` 对齐。这是 P0，必须在写代码前修契约。
2. **需求追踪按逐 ID 解释不可满足**：规格中有 172 个不同 ID、44 个 `AT-*` 场景、12 个任务；追踪矩阵按“范围行”映射，QAL-005 却要求“每个 MUST 级产品需求至少一个 AT 和一个 T”。大量需求没有专属验收，`done` 不可证伪。
3. **绿色启动缺技术选型，且默认栈与需求冲突**：AGENTS 引用的“AGENT_SPEC 选型章节”不存在；默认 PostgreSQL 全文索引的 `ts_rank` 不是 BM25，也没有全局文档频率，无法直接满足 RET-003/RET-006 的 BM25 语义。
4. **质量验收没有人工金标**：QAL-001 要求确定性假模型，M1 又要求真实 50 篇端到端；假模型只能证明契约，不能证明“该不该引用”。DOD-004 的“无依据生成结果为零”在有限样本上不可验证。
5. **全文模式预算语义未定义**：`budget.global_max=120` 是“每查询”还是“每论述”？50 条论述按两种解释会产生 30 倍成本差或召回坍塌；规格没有 per-claim 预算、总成本上限或降级策略。

**一句话判断**：当前规格更像“把设计文档的所有正确性愿望写成 MUST 的长清单”，而不是“可由 coding agent 分片执行、可被证据推翻的实施基线”。需要先做**契约修正、技术选型、质量金标、性能 SLO、追踪自动化**五件事，再进入 M0。

## 1. 评审基线与量化事实

| 指标 | 数值 | 说明 |
|---|---:|---|
| `文献推荐工具_AGENT_SPEC.md` | 1704 行 / 133,226 字节 | 确认事实（`wc`/`ls`） |
| `AGENTS.md` | 410 行 / 34,508 字节 | 确认事实 |
| 不同稳定 ID（`FND/ING/...`） | 172 | 含 CON/API/ERR 等契约 ID；`grep` 去重 |
| `AT-*` 验收场景 | 44 | `grep` 去重 |
| 实现任务 | 12（T00–T11） | 规格 §19 |
| 不变量 | 10（INV-01–10） | AGENTS §4 |
| `MUST` 字样 | 421 处（其中 `MUST NOT` 61 处） | `grep` 计数 |
| `SHOULD` 字样 | 65 处 | `grep` 计数 |
| 测试语料 | 50 篇 / 714 页 | AGENTS:13、SPEC:115-116 |

**基线判断 [事实]**：这不是“规格不够详细”，而是“详细到了不可执行/不可验证”。1704 行里同时包含产品需求、架构 ADR、数据契约、状态机、API、错误码、测试夹具、任务分解和 DoD；这些内容的变更频率与读者不同，却被放在一个文件里，导致任何一处修改都可能触发全局重读。

**外部经验对照 [事实]**：

- GitHub Spec Kit 的官方流程明确要求把工作拆成“small, reviewable chunks，每个任务可独立实现和测试”；本规格的 T03 一个任务就覆盖解析、元数据、章节锚点、两级索引、文献类型、50 篇导入，明显超出“可独立验证”的粒度（[GitHub blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)）。
- Thoughtworks 对 spec-driven development 的评估是“workflows remain elaborate and opinionated”“some generate lengthy spec files that are hard to review”，并提醒“handcrafting detailed rules for AI ultimately doesn't scale”（[Thoughtworks Radar](https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development)）。
- Birgitta Böckeler 的实践评估更直接：冗长 spec 会造成 review overload、false sense of control，agent 会忽略或过度执行指令；她建议小步迭代，而不是大量前置规格（[Understanding Spec-Driven-Development](https://birgitta.info/posts/spec-driven.html)）。
- 对 AGENTS.md 的实证研究（SWE-bench + 开发者提交的 context files）发现：提供 context files **通常不提升任务成功率**，反而平均增加 **20% 以上推理成本**；指令会被遵循，但“仓库概览”类内容没有帮助（[arXiv:2602.11988](https://arxiv.org/abs/2602.11988)）。
- Anthropic 的 agent 工程经验：优先最简单方案；workflow 适合可预定义路径，agent 适合开放、难以预设步骤的问题；agentic 系统通常用延迟和成本换质量（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)）。多 agent 约 **15× chat 的 token**，适合广度并行研究，不适合强共享上下文/强依赖任务（[Multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)）。
- 检索侧的经验也支持“不要凭单一指标选型”：BEIR 发现 BM25 是强基线，reranking/late-interaction 平均最好但计算成本高，dense/sparse 更高效但在分布外常落后（[BEIR](https://arxiv.org/abs/2104.08663)）；MTEB 发现没有单一 embedding 在所有任务上占优（[MTEB](https://arxiv.org/abs/2210.07316)）。因此，embedding/reranker/BM25 的选择必须用本项目的分层基准决定，不能靠排行榜或“算法名称相同”。

这些外部结论不能直接证明本项目该怎么做，但足以支持一个判断：**当前规格的“长而全”不是免费的；它正在用上下文成本和规则冲突换取一种虚假的确定性。**

## 2. P0 发现（阻断，必须先解决）

### P0-01 跨库合并后的 Paper/Evidence 身份契约不成立

**位置**：`文献推荐工具_AGENT_SPEC.md:730`（`paper_id` 库内稳定且全局唯一）、`:756`（Passage 的 `paper_id` 必须与被引用 Paper 一致）、`:776`（Evidence 的 `paper_id` 必须指向同一篇论文）、`:792`（`result_id` 有 DOI 时为 `doi:<doi_normalized>`）、`:796`（`Recommendation.paper` 是单个 `Paper`）、`:482-493`（DED-004 合并 `source_ids`、`evidence_ids`）。

**类型**：[事实] 契约字段如此；[推断] 合并后无法同时满足所有一致性约束。

**失败反例**：

- 库 A 返回 DOI `10.1234/x`，`paper_id=A:123`；库 B 返回同一 DOI，`paper_id=B:456`。
- 协调器按 DOI 合并为 `result_id=doi:10.1234/x`；`Recommendation.paper` 只能选 A:123 或 B:456。
- 若选 A:123，来自 B 的 `Evidence.paper_id=B:456` 与 `Recommendation.paper.paper_id=A:123` 不一致。若实现严格校验 `Evidence.paper_id` 必须指向同一 Paper，B 的证据被拒绝，DED-004 的“合并来源与证据”失败；若不校验，证据溯源断裂，INV-03 的“可回查”失败。
- 更隐蔽的问题：A 和 B 的 `metadata_verified`、作者、年份可能冲突。DED-004 说按“版本化来源优先级和字段级合并规则”处理，但 `Recommendation.paper` 是单个对象，没有字段记录“这个字段来自哪个库、哪个 `paper_id`、哪个 `metadata_source`”。快照冻结后，审计无法还原合并前的两份书目。

**推荐修复**（契约变更，需按 AGENTS §10.2 批准）：

- 把 `Recommendation.paper` 拆成：
  - `canonical_paper`：合并后的展示用书目视图，字段带 `field_provenance`；
  - `paper_sources: [{library_id, paper_id, source_uri, metadata_source, metadata_verified, fields_hash}]`：每个来源库的原始 Paper 引用。
- 或者把 `paper_id` 定义为**全局 work-level ID**，另设 `source_paper_ids: string[]`；`Evidence.paper_id` 仍指向来源库的 Paper，`Recommendation` 用 `canonical_paper_id` 关联。
- 两种方案都必须增加 `AT-DED-004`：两个库同 DOI、不同 `paper_id`、不同元数据，断言合并后证据可回查、字段来源可审计、快照不丢来源。

**收益/代价**：

- 收益：恢复 INV-03/INV-08 的可验证性；让“合并”从口号变成可审计数据；避免快照丢来源。
- 代价：Schema、迁移、前端卡片、快照哈希都要改；约 3–5 人日 + 契约评审。
- 采用条件：在 T02 契约冻结前完成；否则 T05/T07 会基于错误契约写测试，返工更大。

### P0-02 需求数量远超 AT 数量：QAL-005 按逐 ID 解释不可满足

**位置**：`文献推荐工具_AGENT_SPEC.md:1510`（QAL-005：每个 MUST 级产品需求至少映射一个 `AT-*` 和一个 `T*`）、`:1604-1620`（追踪矩阵按范围行映射，例如 `:1609` 一行把 ING-001～008 + IDX-001～005 共 13 个需求映射到 3 个 AT 和 T03）。

**类型**：[事实] 规格中有 172 个不同 ID（含大量 MUST 级产品/接口需求）、44 个 AT，矩阵按范围行映射；[推断] 大量需求没有专属验收，完成判定不可证伪。

**限定**：172 个 ID 中包含 CON/API/ERR 等契约 ID，不是每个都需要独立的“产品验收场景”。但即使只数 FND/ING/IDX/RET/BUD/STR/SCR/DED/RANK/SNAP/EVAL/EVD/CIT/INS/UI/SEC/CFG/OBS 这些需求域，数量也远大于 44；QAL-005 的逐 ID 解释不可满足，按范围解释则 QAL-005 被架空。

**失败反例**：

- `API-002` 要求 `Idempotency-Key`、`202`、输入校验、`400 VALIDATION_ERROR`；唯一相关的 `AT-API-001` 只写“创建搜索、读取当前状态、订阅 SSE、创建快照和导出”，没有断言“相同 key 不同请求哈希返回 `IDEMPOTENCY_KEY_CONFLICT`”。实现者可以让 `AT-API-001` 通过，而幂等冲突完全错误。
- `STR-006` 要求有界队列与背压；没有任何 AT 断言“队列满时只阻塞对应生产者，不全局死锁”。
- `EVT-003` 要求 `(query_id, event_id)` 与 `(query_id, sequence)` 唯一、相同 event_id 不同载荷返回 `EVENT_ID_CONFLICT`；没有专属 AT。
- `OBS-002` 要求 10 个指标；没有 AT 断言这些指标真的被暴露、标签基数受控、首条结果指标不被长尾覆盖。
- `CFG-001` 要求启动校验；没有 AT 断言“非法配置快速失败并指出字段”。

**为什么这不是“补几个测试”**：QAL-005 的“每个 MUST 级产品需求”是逐 ID 的，而矩阵是范围行的。范围行只能证明“这个范围内至少有一个场景”，不能证明“每个 ID 都有”。按当前 172 个 ID、44 个 AT 的比例，即使把每个 AT 都当成 3 个需求的覆盖，也远不足。

**推荐修复**：

1. 建立机器可读的 `requirements.yaml`：每个 ID 的级别（MUST/SHOULD/MAY）、所属域、验收 ID、测试名、状态。
2. 测试命名强制包含 ID（例如 `test_API_002_idempotency_conflict`），CI 用 `pytest --collect-only` 或等价命令扫描；没有对应测试的 MUST ID 直接失败。
3. 追踪矩阵由脚本从 `requirements.yaml` + 测试收集结果生成，不再手工维护。
4. 先覆盖**高风险 30 个 ID**（API 幂等/重放、STR 背压/取消/重试、EVT 冲突/缺口、SNAP 迟到、SEC 上传/删除、OBS 指标、CFG 校验），不要一次给 172 个 ID 补测试；其余按里程碑推进。
5. 把 SHOULD/MAY 从“每个必须有正向测试”的规则中分离，避免 AGENTS §6.2 的过度解释。

**收益/代价**：

- 收益：`done` 从“文档说完了”变成“可检索的测试证据”；防止范围行掩盖缺口。
- 代价：约 1–2 周建立 registry + CI 门禁；之后每个需求多写一个测试名，边际成本低。
- 采用条件：T00/T01 完成；否则 M0 的“契约测试通过”无法证明。

### P0-03 缺技术选型；默认 PostgreSQL FTS 不是 BM25

**位置**：`AGENTS.md:237-239`（“首期技术栈以 AGENT_SPEC 的选型章节为准；SPEC 未指定时采用设计文档 §15.1 的首期建议”）、`:246`（新增依赖前先证明现有依赖无法满足）、`:331`（依赖清单属于契约区）；`文献推荐工具_AGENT_SPEC.md:133-158`（只有目录名与注释，没有版本/库选型）、`:240`（RET-003 记录 BM25/向量 TopK）、`:243`（RET-006 使用 RRF）。

**类型**：[事实] AGENTS 引用的“选型章节”在 SPEC 中不存在；[事实] PostgreSQL 官方文档明确 `ts_rank` 不使用全局信息，无法做公平归一化；[事实] ParadeDB 文档明确 PostgreSQL 内置 FTS 缺少 BM25 的全局文档频率；[推断] 默认栈无法直接满足 RET-003 的 BM25 语义。

**失败反例**：

- T01 按 AGENTS 回退到“PostgreSQL + 全文索引 + pgvector”；T04 实现关键词路时使用 `ts_rank`/`ts_rank_cd`。
- AT-RET-001 要求“精确术语可由关键词路召回”，`ts_rank` 可以做；但 AT-EVAL-001 要求报告 `Recall@K` 与融合排序，团队会把 `ts_rank` 当作 BM25 报告，指标不可比。
- 后续发现 `ts_rank` 没有 IDF，换成 ParadeDB `pg_search` 或 OpenSearch；这改变依赖、索引 schema、查询语法。AGENTS §10.2 把依赖清单列为契约区，换引擎需要批准 + 迁移，M2 被卡住。
- 更糟：不同实现者分别选 `ts_rank`、ParadeDB、OpenSearch，产生三套 `retrieval_score` 口径，违反 SCR-001 的“异构原始分不可直接比较”。

**推荐修复**：

- 在 T00/T01 之间增加 **T00.5“技术选型 ADR + spike”**，至少锁定：
  1. PDF 解析/OCR（PyMuPDF、GROBID、MinerU、Docling 的 bake-off）；
  2. 关键词/BM25 引擎（PostgreSQL 内置 FTS 仅作 fallback；ParadeDB `pg_search` / OpenSearch / VectorChord-BM25 三选一）；
  3. 向量索引（pgvector HNSW vs Qdrant）与参数；

### P0-04 质量验收缺人工金标；假模型只能证明契约

**位置**：`文献推荐工具_AGENT_SPEC.md:1506`（QAL-001 使用确定性假模型）、`:1508`（QAL-003 M2 起真实 API/SSE/前端）、`:116`（M1 使用真实 50 篇语料端到端）、`:1596`（AT-EVAL-002 要求证据支持率、专家采纳、无依据引用句次数）、`:1677`（DOD-004 “无依据生成引用句的验收结果为零”）。

**类型**：[事实] 测试策略如此；[推断] 假模型无法证明语义质量；[推断] 50 篇不足以做分主题/分库校准切片。

**失败反例**：

- `worker_gate` + 固定假 verifier 让所有 AT-EVD-001～004 通过；真实模型在 50 篇上把 60% 的 `support` 判成 `insufficient`，或把“主题相似”判成 `support`，并生成看似有证据的引用句。测试全绿，产品不可用。
- DOD-004 要求“无依据生成引用句的验收结果为零”。任何有限样本都可能偶尔出现一次；如果出现一次，是否整个 M4 失败？如果样本只有 20 条，零失败也不能证明总体错误率低于 1%。这是把统计问题写成了布尔断言。
- AT-EVAL-003 要求“按库、主题和输入类型报告校准误差、Brier 分数”；50 篇论文按主题切分后每片可能只有 5–10 条，Brier 的置信区间宽到无法决策。

**推荐修复**：

- 分三层测试，不要把三层混成一个“通过”：
  1. **L0 契约/流水线**：假模型、可控 Worker、事件重放；证明状态机、幂等、快照、排序、错误码。
  2. **L1 语义质量**：200–300 条人工标注的 `claim → paper → evidence → relationship` 金标，双人标注 + 仲裁，报告 Cohen's κ / Krippendorff's α（目标 ≥0.7）；分层覆盖 support/complement/contrast/insufficient、综述/原始论文/撤稿、关键词/摘要/全文。

- 把 DOD-004 改为可证伪的统计断言：例如“在 200 条分层样本中，无依据引用句的 95% 置信上界 < 2%”；并逐例列出失败。
- 用公开检索基准（BEIR/SciFact/SciDocs）只校准**检索组件**，不要拿它证明端到端引用质量；领域金标必须自己标。
- 评估报告必须区分“未运行 / 失败 / 跳过 / 通过”，并给出样本量与置信区间。

**收益/代价**：

- 收益：把“证据驱动”从文档口号变成可测量能力；避免 fake tests 制造虚假完成。
- 代价：标注 200–300 条约 2–4 人周（含仲裁）；L2 用户研究约 1–2 周。
- 采用条件：M1 质量门禁前必须建立；否则 M1 只能证明“能跑”，不能证明“值得引用”。

### P0-05 全文模式预算/成本语义未定义

**位置**：`文献推荐工具_AGENT_SPEC.md:266`（`N_i` 是第 i 个库最多进入重排/核验的候选数）、`:273`（BUD-004 `budget.global_max`）、`:1432`（默认 `120`）；`Recommendation.claim_id` 在 `:794`；全文模式“先聚类和去重相似论述，再批量生成查询向量”在 `:232`。

**类型**：[事实] 没有 per-claim 预算字段；[推断] 实现者会做两种互斥解释，导致成本或召回数量级差异。

**失败反例**：

- 解释 A：`global_max=120` 是每个 query 的总候选。一篇全文有 30 条论述，每条平均 4 个候选；一篇关键论文可能因为预算被分到别的论述而漏掉，召回坍塌。
- 解释 B：`global_max=120` 是每条 claim 的预算。30 条论述 × 120 = 3,600 个候选；每个候选 1 次 rerank + 1 次 LLM 核验，按 2k tokens/次、$3/M tokens 估算，单查询可能数十美元；如果并发 10 个查询，成本失控。
- 解释 C：实现者按库分配 120，但全文模式有 5 个库，实际 600；仍然没有总上限。
- 无论哪种，AT-EVAL-005 只测“首条有效推荐/最终快照”，没有测“每条 claim 的召回”或“单查询成本”，所以测试无法发现解释错误。

**推荐修复**：

- 明确 `budget` 的两级语义：
  - `budget.query_total_max`：单次搜索所有 claim、所有库的高成本候选总上限（默认 240）；
  - `budget.per_claim_min/max`：每条 claim 的候选上下限（默认 8/40）；
  - `budget.per_library_min/max`：保留现有；
  - 分配顺序：先按 claim 重要性/覆盖度分配，再按库权重分配；未用完的 claim 预算可回收，但必须记录。
- 增加 `budget.max_model_tokens_per_query`、`budget.max_cost_usd_per_query`、`budget.degrade_policy`（例如超过 80% 预算时只对头部候选做 LLM 核验，其余标记 `verification_deferred`，不得进入可引用列表）。
- 增加 `AT-BUD-001`：30 条 claim、5 个库、总预算 240，断言每条 claim 至少 N 个候选、总候选 ≤240、成本 ≤上限；两种解释下结果必须一致。
- 在快照记录 `budget_usage`（候选数、token、估算成本、降级次数）。

**收益/代价**：

- 收益：把“成本”从不可见变成可配置、可审计；避免全文模式成为烧钱入口。
- 代价：预算分配器复杂度上升；需要产品确认“全文模式愿意花多少钱”。
- 采用条件：M2 全文模式前；否则性能/成本基准没有共同口径。

### P1-02 Agent 的预算/停止权与确定性策略冲突；Skill 契约缺失

**类型**：[事实] 权属重叠；[事实] Skill 契约缺失；[推断] Agent 的决策不可复现，预算测试无法写。

**失败反例**：

  - `stop_recommendation`（可选，附理由和风险标记）。

- 补 `packages/skill/SKILL.md`：工具列表（名称、输入/输出 Schema）、何时调用/禁止调用、终止条件、错误处理、预算交互、3–5 个评测用例。AGENTS §10.2 已把“Citation Skill 工具 Schema 与终止条件”列为契约区，但 SPEC 没有给出内容；这是 T02/T07 的前置产物。

### P1-03 无绝对性能 SLO；默认 120 候选/60–90s 未验证

**位置**：`文献推荐工具_AGENT_SPEC.md:1421`（`worker.soft_deadline_ms=60000`）、`:1439`（`hard_deadline_ms=90000`）、`:1432`（`global_max=120`）、`:1461-1469`（OBS-002 指标但没有目标值）；`AGENTS.md:71`（INV-01 的性能判据是“接近最快合格 Worker”，是相对判据）。

**类型**：[事实] 没有绝对 SLO；[推断] 默认参数会让首结果被 LLM 核验支配。

**失败反例**：

- 5 个库 × 每库 10 个候选 = 50 个候选；每个候选 1 次 rerank（200ms）+ 1 次证据读取（300ms）+ 1 次 LLM 核验（2s）。单库 8 并发，10 个候选约 3s；但 5 个库共享 provider 速率限制 20 QPS，实际排队；p95 首条有效结果 8–12s，最终 70–95s。
- 用户输入一个关键词，期望 2–3s 看到结果；系统却按全文模式等 60s。INV-01 只说“比最慢库快”，没有说“用户等多久算合格”，所以测试无法判失败。
- `model.call_timeout_ms=45000` 比 `soft_deadline_ms=60000` 只小 15s；一个模型调用慢，就可能把整个 Worker 拖到软截止，首结果被拖累。

**推荐修复**：

- 按输入模式定义 SLO（示例，需产品确认）：
  - 关键词：TTFF p50 ≤ 3s、p95 ≤ 8s；TTFC p95 ≤ 15s；最终快照 p95 ≤ 30s。
  - 摘要：TTFF p95 ≤ 10s；最终 p95 ≤ 60s。
  - 全文：TTFF p95 ≤ 15s；最终 p95 ≤ 120s；每条 claim 至少 1 条 verified 的时间 p95 ≤ 30s。
  - 吞吐：5 并发查询时，p95 TTFF 退化 ≤30%；20 并发时服务不崩溃、有明确降级。
  - 成本：关键词 ≤$0.05/query；全文 ≤$0.50/query（按实际模型价格校准）。
- 增加阶段延迟预算：检索 300ms、rerank 800ms、证据读取 500ms、LLM 核验 2.5s、评分/去重 100ms；每阶段超时单独记录。
- 增加 `AT-EVAL-007`：5 库、慢库闩锁、provider 429、模型超时四种场景，断言 p95 SLO 与降级行为。
- 如果 SLO 达不到，允许“检索候选先展示但标注未核验、不可引用”，这满足 INV-03/INV-07；不要用假流式或延迟快库结果来“看起来快”。

**收益/代价**：

- 收益：性能从“相对比较”变成“可验收”；用户等待有上限；成本可预算。
- 代价：需要容量规划与产品取舍；可能需要更便宜的 verifier 或 NLI 预筛。
- 采用条件：M1 前定关键词 SLO；M2 前定全文 SLO。

### P1-04 逐字证据的 span 生成方式未定义，精确字节匹配易假阴性

**位置**：`AGENTS.md:92`（`Evidence.quote` 必须等于 `Passage.raw_text` 指定 UTF-8 字节区间）、`文献推荐工具_AGENT_SPEC.md:777-786`（quote/offset/source_trace_valid）、`:1181-1189`（EVD-002 核验程序前后各检查一次，规范化只用于定位）。

**类型**：[事实] 约束如此；[推断] 如果让 LLM 自由生成 `quote`，精确匹配会大量失败；如果实现者放松匹配，`source_trace_valid` 语义被破坏。

**失败反例**：

- PDF 原始文本含连字 `ﬁ`、软连字符、行尾断词 `pre-\nmRNA`；模型返回 `pre-mRNA`；按 UTF-8 字节切片严格比较失败，候选被错误拒绝。
- 模型返回的是对原文的轻微改写（同义替换、补全缩写）；严格比较失败；实现者为了通过测试改成“规范化后相等”，但 `quote` 已不等于 `raw_text` 切片，INV-03 被绕过。
- 双栏 PDF 的 `raw_text` 按 PDF 内容流顺序交错两栏；模型从阅读顺序摘出的句子在字节区间中不存在；严格比较失败或定位到错误段落。

**推荐修复**：

- 证据不是“模型生成 quote”，而是“模型从预分割的 span 列表中选择 span_id”：
  - 入库时把 `Passage.raw_text` 切成句子/子句 span，保存 `span_id`、`[start,end)`、`text_hash`、`normalized_hash`；
  - 模型只输出 `passage_id + span_id`（或多个 span_id + 关系），服务端用 span 重建 `quote`；
  - 对跨 span 的引用，允许 `span_ids[]` + `join_rule`，但必须由服务端拼接并记录。
- 增加 `trace_kind`：`pdf_exact`、`pdf_normalized`（附规范化版本与映射）、`api_snippet`、`ocr_low_confidence`；不要再用一个布尔值表达所有情况。`source_trace_valid=true` 只对 `pdf_exact`/可审计的 `pdf_normalized` 成立；`api_snippet` 只能标注“API 摘要片段，非 PDF 原文”。
- 解析器必须输出 reading-order 与坐标；双栏/跨栏用版面感知解析（见 P1-08）。
- 增加 `T-INV-03.byte_span_ligature`、`T-INV-03.cross_column`、`T-INV-03.ocr_low_confidence`。

**收益/代价**：

- 收益：证据召回提高；`source_trace_valid` 不再依赖模型“猜对字节”；审计可解释。
- 代价：入库多一层 span 表；模型提示词改为“选 ID”而不是“抄原文”；Schema 变更。
- 采用条件：T03 入库设计时；否则 T05 会围绕错误接口写测试。

### P1-05 `display_score` 预测目标未定义（相关性 vs 引用价值）

**位置**：`文献推荐工具_AGENT_SPEC.md:378-409`（SCR-003/004/005：共同重排、校准到 0–100）、`:639`（EVAL-003 报告 Brier/校准误差）；`AGENTS.md:50`（统一展示分是“跨库展示与排序分数，不是引用正确率”）。

**类型**：[事实] 规格只说“相关性分”，没有标签定义；[推断] 校准器无法训练，或者训练出的分数与用户任务不一致。

**失败反例**：

- 两条候选都通过证据门槛：A 是一篇高相关综述，适合作为背景引用；B 与用户段落主题高度相似，但只是重复用户已说的内容，引用价值低。按“主题相关性”打分，B 可能高于 A；用户看到排序后选择了 B，编辑认为没有新增信息。
- 按“引用价值”标注训练，但评估时用“主题相关性”金标，Brier 分数很好，产品指标（引用采纳率）很差。
- 校准器在“相关性”标签上训练，UI 文案写“统一相关性分”，用户却把它当“应引用概率”；这是 AGENTS 明确禁止的，但分数的语义没有阻止这种误读。

**推荐修复**：

- 产品必须先定义 `display_score` 的预测目标，二选一：
  - **方案 A（推荐）**：`citation_utility`——在当前 claim 上下文中，“这条文献值得被引用”的等级（0=不引用，1=背景，2=直接支持，3=关键证据）；证据资格是前置门槛，分数只在合格集合内排序。
  - **方案 B**：`topical_relevance`——仅表示主题相关性；另设 `citation_utility` 作为独立字段/分组，不混为一个分数。
- 无论哪种，写清标签 rubric、标注流程、一致性指标、训练/验证切分；`score_version` 绑定标签版本。
- 如果短期没有标注，保持 `calibration_status=bootstrap`，UI 只显示“排序分”，不显示“概率”；不要把 bootstrap sigmoid 当校准概率。
- 增加 `AT-EVAL-008`：同一 claim 下“高相关但低引用价值”和“中相关但高引用价值”两条候选，断言排序符合定义的标签，而不是只符合主题相似度。

**收益/代价**：

- 收益：分数终于有可训练、可评估的目标；避免“相关但没用”的推荐。
- 代价：标注成本；如果选方案 A，需要重新定义 UI 文案与校准器。
- 采用条件：M1 评分前；这是产品决策，不是实现者能自行决定的。

### P1-06 每库全流程 Worker 缺全局限流/批处理，易被 LLM 速率与长尾支配

**位置**：`文献推荐工具_AGENT_SPEC.md:90`（ADR-003 每库独立 Worker）、`:290-291`（STR-001/002 并行、逐条/小批发布）；`AGENTS.md:47`（Worker 是围绕单个库的并行处理单元）。

**类型**：[事实] 架构如此；[推断] 5 个库 × 8 并发 = 40 个 LLM/重排调用，容易触发 provider 限流；没有全局 token bucket 或跨库优先级。

**失败反例**：

- 5 个库同时启动，每个库 8 并发，共 40 个 LLM 核验请求；provider 限制 20 QPS，后 20 个请求排队/429；重试放大延迟；快库的首条结果被慢库的请求挤占。
- 某个库的 reranker 是本地 GPU，多个 Worker 同时调用导致显存不足；没有全局批处理，GPU 利用率低但延迟高。
- 慢库的长尾请求占满连接池；协调器无法区分“慢库的无关候选”和“快库的高价值候选”，因为预算在启动时已分配。

**推荐修复**（替代架构 A1，见 §5）：

- 保留“每库检索 Worker”，但把高成本的 rerank/verify 抽成**共享验证池**：
  - 检索 Worker 产出候选到按 query 分区的优先队列；
  - 共享池按 query 公平调度（每 query 至少 1 个槽位），按 batch（4–8）调用 reranker/LLM；
  - 结果逐条回协调器，仍然满足 INV-01（无全局屏障、逐条发布）。
- 或者，如果不改架构，至少增加**全局 token bucket/rate limiter**：按 provider、按 query、按库三层限流；每库并发不再独立，而是从全局配额申请。
- 增加 `worker.max_concurrent_model_calls`、`model.provider_qps`、`model.provider_tpm`、`worker.queue_priority` 配置。
- 增加 `AT-STR-006`：5 库、provider 20 QPS、一个慢库；断言快库首条不被慢库挤占，p95 TTFF 在 SLO 内，无 429 雪崩。

**收益/代价**：

- 收益：吞吐/成本/尾延迟更好；provider 限流可控；GPU 批处理利用率高。
- 代价：多一个共享池服务；跨库公平性与故障隔离更复杂；可能违反“Worker 只访问本库”的字面边界（可用“服务”而非“Worker”规避）。
- 采用条件：≥3 个库或 ≥10 QPS；先用 E4 实验验证，不满足则保留每库 Worker + 全局限流。

### P1-07 认证/租户模型缺失，SEC-001 无法落地

**位置**：`文献推荐工具_AGENT_SPEC.md:1360-1362`（SEC-001 所有接口验证用户、租户、对象归属）、`:1076-1081`（API-008 私有稿件接口）。

**类型**：[事实] 规格没有身份提供方、token 格式、角色、租户配置、RLS 策略；[推断] 实现者会用临时 header 或自制 JWT，安全测试无法覆盖真实攻击面。

**失败反例**：

- 实现者用 `X-User-ID` 请求头做授权；AT-SEC-001 用两个固定用户通过，但生产环境任何人可伪造 header 读取他人稿件。

**推荐修复**：

- 在 `docs/adr/tech-selection.md` 记录选择与威胁模型；不要把认证做成 T10 的“最后补”。

**收益/代价**：收益是 M4 安全门禁可过；代价是 1–2 周基础设施 + 每个 API 的授权测试。采用条件：M1 前至少完成“单租户 + 用户级授权”，M4 前完成多租户。

### P1-08 PDF 解析与 Word/OOXML 编辑的技术栈缺失

**位置**：`文献推荐工具_AGENT_SPEC.md:212-213`（ING-004/005：原始文本、清洗映射、页码、坐标、双栏/断词/OCR）、`:1296`（INS-004：不得全局字符串替换，必须保留域代码、批注、修订）、`:1304`（INS-006：原子导出）。

**类型**：[事实] 规格要求高保真；[事实] 没有选解析器/文档库；[推断] 常见库无法同时满足。

**失败反例（解析）**：

- 用 PyMuPDF 的 `get_text("text")` 处理双栏 PDF，两栏文本交错；`raw_text` 的字节顺序不是阅读顺序；证据 span 跨栏，引用句读起来是乱的。字节匹配可能通过，但语义错误。
- 用纯文本解析器处理扫描 PDF，没有 OCR；`raw_text` 为空或乱码；证据定位失败，M1 的 50 篇里可能有多篇扫描件。
- 用 GROBID 处理非标准版式，章节路径缺失；`section_path` 为空，UI 无法显示章节；AT-EVD-002 只测“错页/篡改”，不测“章节缺失”。

**失败反例（Word）**：

- 用 `python-docx` 查找并替换 `[1]` 文本；它不保留域代码、批注、修订，交叉引用断裂；AT-CIT-001 在简单 fixture 上通过，真实稿件损坏。
- 用全局正则替换数字；把年份 `[2024]`、化学式 `[Fe]` 也替换；INS-004 明确禁止，但测试没有覆盖。
- 用 LibreOffice 转 PDF 再转回 docx；样式、编号、域丢失；无法满足“域代码、批注、修订必须保留”。

**推荐修复**：

- 解析 bake-off（E9）：PyMuPDF、GROBID、MinerU、Docling；用 10 篇代表性 PDF（双栏、表格、扫描、跨页）测：阅读顺序、章节路径、坐标覆盖、表格/图注、速度、许可证。选主解析器 + OCR fallback；记录 `parser_version`、`ocr_confidence`。
- Word 导出 bake-off（E10）：`python-docx`、`docx4j`（Java）、LibreOffice UNO、Office JS API；用含域代码、批注、修订、交叉引用的复杂 docx 测 round-trip；无法保留的结构按 INS-004 输出“变更清单 + 不支持说明”，不得静默损坏。
- 在契约中增加 `parse_quality`（`exact`/`normalized`/`ocr_low_confidence`/`layout_ambiguous`），让证据门槛可以按质量降级。
- 增加 `AT-ING-001`（双栏/跨页/断词）、`AT-INS-008`（复杂 docx round-trip）。

**收益/代价**：收益是 M1/M3 的核心能力可落地；代价是 2–3 周 spike + 许可证评估（GROBID/Docling 开源，docx4j 是 Java 依赖）。采用条件：T03/T08 前。

### P1-11 事件序号“严格 +1”与重放保留窗口未定义

**位置**：`文献推荐工具_AGENT_SPEC.md:936`（`sequence` 在每个 query 内严格递增且步长为 1）、`:963-968`（outbox 同事务、`(query_id, sequence)` 唯一）、`:973`（`Last-Event-ID` / `after_sequence`、`REPLAY_GAP`）。

**类型**：[事实] 约束如此；[推断] 数据库事务回滚/并发分配会导致序号缺口；没有保留窗口，`REPLAY_GAP` 永远不会触发或触发错误。

**失败反例**：

- 协调器用 `nextval` 分配 sequence，事务回滚后序号跳过；客户端收到 1,2,4，认为 3 丢失，触发全量重建；重建后 `latest_sequence=4`，但 3 永远不存在。
- 多个协调器实例处理同一 query（故障转移/重试）同时分配 sequence；唯一约束冲突，或顺序与提交顺序不一致；客户端看到 5 在 4 之前。
- 没有定义事件保留多久；客户端 2 小时后重连，`after_sequence` 仍在窗口内但事件已被清理；服务返回空重放，客户端状态陈旧。
- SSE 消费者慢，服务端没有背压；outbox 堆积，事件延迟增长，首结果指标被污染。

**推荐修复**：

- 每个 query 一个单写者（coordinator lease/fencing token）；sequence 由 per-query 计数器行 `SELECT ... FOR UPDATE` 分配，与结果变更同事务提交；允许回滚产生缺口，客户端用 `sequence > after_sequence` 而非“连续”判断。
- 明确保留窗口：`event.retention_hours`（例如 query 结束后 24h）或 `event.max_events_per_query`；超过窗口返回 `REPLAY_GAP`，客户端全量重建。
- 增加 `event.backpressure`：outbox 队列长度阈值、SSE 发送超时、慢消费者断开；慢消费者不得阻塞协调器。
- 增加 `AT-EVT-003`：事务回滚、并发写、2 小时重连、慢消费者四种场景，断言无重复/无丢失/状态可重建。

**收益/代价**：收益是事件语义真正可执行；代价是 per-query 锁可能限制吞吐（但 120 结果规模足够）。采用条件：T07 前。

### P1-12 文献类型资格/元数据核验/快照权限撤销缺治理规则

**位置**：`文献推荐工具_AGENT_SPEC.md:210`（ING-002 元数据交叉核验）、`:211`（ING-003 文献类型/撤稿）、`:740`（`document_type_eligible`）、`:746`（`metadata_verified`）、`:1360`（SEC-001）、`:1397`（SEC-007 删除）。

**类型**：[事实] 只有布尔字段和原则，没有规则矩阵；[推断] 实现者会各自解释，资格门槛不可复现。

**失败反例**：

- `document_type_eligible` 由“策略”计算，但规格没说综述/编辑/会议摘要/预印本是否允许；实现者 A 允许综述，B 禁止；同一 query 在两个部署得到不同可引用集合。
- `metadata_verified` 只要求“完成规定核验”，但没规定核验哪些字段、用什么源、冲突怎么办；实现者把“有 DOI”当 verified，作者/年份错误仍进入引用。
- 用户曾有权访问库 A，创建快照后权限被撤销；快照仍包含 A 的证据。SEC-001 说事件重连要重新授权，但快照是不可变的；如果按当前权限过滤，快照不再可重现；如果不按，撤销后仍泄露内容。
- 私有稿件 24h 后删除，但快照引用 `manuscript_context_version`；导出时稿件已删除，无法重现插入位置。

**推荐修复**：

- 定义 `document_type_policy` 矩阵：按输入模式（关键词/摘要/全文）× 类型（research/review/correction/retraction/editorial/other）给出 `eligible`/`context_only`/`excluded`，版本化；撤稿永远 `excluded`；更正声明默认 `context_only` 并关联原论文。
- 定义 `metadata_verification` 对象：`sources[]`、`fields_checked[]`、`conflicts[]`、`verified_at`、`verifier_version`；`metadata_verified=true` 必须有完整字段级证据；缺字段时 `metadata_verified=false` 并给出 `missing_fields`。
- 快照记录 `access_scope`（创建时的 tenant/library ACL）；读取时做“双重检查”：当前权限 + 快照范围；若权限已撤销，返回脱敏快照/明确错误，而不是静默泄露或静默删内容。记录 `access_revoked_at`。
- 稿件删除时，快照保留 `manuscript_context_hash` 和必要的锚点元数据；导出若需要原文，返回 `MANUSCRIPT_DELETED`，不得用缓存全文绕过删除。
- 增加 `AT-SEC-006`（快照权限撤销）、`AT-ING-002`（元数据冲突/缺失）、`AT-ING-003`（类型矩阵）。

**收益/代价**：收益是资格门槛可复现、权限撤销可解释；代价是策略配置与测试矩阵。采用条件：M1 前类型/元数据；M4 前权限撤销。

## 4. P2 发现（中风险，建议在对应里程碑前处理）

### P2-01 `round1` 舍入模式跨语言不一致

**位置**：`文献推荐工具_AGENT_SPEC.md:379`（`round1(100 × Calibrate_global(r))`）、`:685`（分数为有限数值，范围 [0,100]）。

**失败反例**：Python `round(91.45, 1)` 可能得到 91.4（banker's rounding），JavaScript `Math.round(91.45*10)/10` 得到 91.5；同一结果在服务端与前端显示不同，快照哈希不同。**修复**：明确“四舍五入远离零”或“half-up”，用整数运算 `floor(x*10+0.5)`（正值域）；在契约测试里加 91.45、0.05、99.95 三个边界。

### P2-02 去重规则版本变化可能改变 `result_id`

**位置**：`文献推荐工具_AGENT_SPEC.md:466`（`stable_id` 可用规范化键或带版本前缀哈希）、`:476`（回退键带规则版本）、`:792`（`result_id` 有 DOI 时为 `doi:<doi>`）。

**失败反例**：标题规范化规则从 v1 升到 v2，无 DOI 论文的 `result_id` 变化；用户旧快照中的选择指向旧 ID，新搜索出现重复卡片。**修复**：`result_id` 一经分配不可变；`dedup_key` 可版本化；维护 `result_id_alias` 表，旧 ID 映射到新 ID；快照保留旧 ID。

### P2-03 导出文件是否含 `export_id` 未定义，影响“重复导出一致”

**位置**：`文献推荐工具_AGENT_SPEC.md:1304`（每次导出绑定 snapshot/selection/style/result version）、AGENTS:108（同一快照重复导出，除时间戳与文件名外内容一致）。

**失败反例**：导出 JSON 含随机 `export_id` 或 `generated_at`，两次导出字节不同；测试按“语义等价”通过，但按 INV-04 的“字节级或规范化 JSON 等价”失败。**修复**：定义导出 artifact schema；把 `export_id`、`generated_at` 放入文件名/元数据，不放入内容；内容哈希只覆盖稳定字段；加 golden-file 测试。

### P2-04 AGENTS 对 LangGraph 的字面禁令与 LangChain v1 运行时冲突

**位置**：`AGENTS.md:129`（禁止“把 LangGraph 多节点编排设为运行时必需”）、`文献推荐工具_AGENT_SPEC.md:89`（ADR-002 选 LangChain 单 Agent）。

**事实**：LangChain v1 官方文档明确 `create_agent` 是“built on LangGraph”；用 LangChain 标准 agent 就会引入 LangGraph 依赖。**修复**：把禁令改为“禁止业务层定义多节点/多角色图编排；允许 LangChain agent loop 的底层运行时依赖”；在依赖清单中注明 LangGraph 是传递依赖，不作为业务编排接口。

### P2-05 证据 `context` 无长度上限，版权/存储风险

**位置**：`文献推荐工具_AGENT_SPEC.md:779`（`context` 必填，不得通过拼接改变原意）、`:1415`（`evidence.max_display_chars=1200` 只限制展示）。

**失败反例**：`context` 保存整页或整节，超出期刊授权范围；存储膨胀；日志/导出泄露过多原文。**修复**：增加 `evidence.max_context_chars`（例如 2000）、`evidence.max_total_chars_per_recommendation`；超出时截断并标记 `context_truncated=true`，但不得改变 `quote` 定位；版权策略按合作方授权配置。

### P2-06 追踪矩阵“唯一位置”与 SPEC“必须扩展”冲突，流程会堵

**位置**：`AGENTS.md:230`（实现 Agent 不直接改矩阵）、`文献推荐工具_AGENT_SPEC.md:1604`（新增需求必须在同一变更中扩展本表）。

**失败反例**：实现 Agent 发现某需求缺 AT，按 AGENTS 不能改矩阵，按 SPEC 必须改；它选择不改，矩阵继续缺；或它改了，违反 AGENTS。**修复**：矩阵改为生成物；实现 Agent 只改 `requirements.yaml` 和测试名，CI 生成矩阵；主控审阅生成 diff。这样既避免并发写冲突，又满足“同一变更扩展”。

## 5. AGENTS.md 专项审查：是否过长、自相矛盾、阻止开发

### 5.1 结论

**是，三个问题都存在，但“长度”不是唯一的、也不是最严重的。**

- **过长**：410 行 / 34.5KB，且与 1704 行 SPEC 大量重复；每个任务要求通读 SPEC，上下文成本高。外部实证不支持“越长越好”：context files 平均增加 20%+ 推理成本，通常不提升成功率；实践者反复指出冗长 spec 导致 review overload 和指令忽略。
- **自相矛盾**：至少 6 处（tie-breaker、第二真源、矩阵所有权、命令表 bootstrap、依赖审批、LangGraph 字面禁令）。其中 tie-breaker 会直接改变排序结果，是 P1。
- **阻止开发**：4 个机制会卡住绿色启动：命令表为空 + 只允许仓库命令；每条需求测试 + 默认测试集；每个新依赖证明 + 契约审批；实现者不能改矩阵但 SPEC 要求改。不是“不能做”，而是“先做大量非代码工作，且规则互相等待”。

### 5.2 建议的 AGENTS 结构（≤150 行）

| 区块 | 内容 | 行数上限 |
|---|---|---:|
| 1. 作用与优先级 | 用户指令 > SPEC > AGENTS > 设计文档；冲突升级路径 | 12 |
| 2. 不变量 | INV-01～10：一句话 + 违反判据 + `T-INV-*` 测试名 | 45 |
| 3. 写入范围/契约区 | 白名单、契约区清单、变更批准 | 15 |
| 4. 依赖与代码纪律 | baseline 预批准、版本锁定、确定性服务禁 LLM | 20 |
| 5. 安全/隐私 | 租户、私有稿件、日志、凭据、生产边界 | 20 |
| 6. 验证与报告 | 命令表、分层验证、报告分档 | 25 |
| 7. 维护 | 失效引用检查、生成物、变更记录 | 8 |

**关键改动**：

- 删除 INV 段中的需求细节，只保留 ID + 判据 + 测试名；细节回 SPEC。
- 增加“T01 bootstrap 例外”和“baseline 依赖预批准”。
- 报告分档：里程碑/契约变更用完整 8 节；普通改动用 3 节。
- 增加“引用完整性 lint”：AGENTS 中提到的章节/文件必须存在；禁止“选型章节”这类空引用。
- 增加“重复短语 lint”：AGENTS 与 SPEC 的连续 20 token 重叠超过阈值时警告。

### 5.3 是否应该合并 AGENTS 与 SPEC？

**不建议合并**。两者职责不同：SPEC 是需求/契约真源，AGENTS 是工程纪律/不变量。但应**去重**：AGENTS 只保留“不可破坏的约束”，不复制需求正文。合并会让 1704 行变成 2000+ 行，且需求变更频率与纪律变更频率不同。

### 5.4 门禁（M0–M4）评估与重构

**当前门禁的问题 [事实]**：M0–M4 的“完成判据”是功能清单（`文献推荐工具_AGENT_SPEC.md:113-119`），没有量化退出标准、没有证据包格式、没有红队/故障注入的强制项、没有性能基线。结果是“功能演示”可以代替“质量证明”，而 DOD-001～010 又把所有质量要求堆到最后。

**建议的门禁结构**：

| 门禁 | 必须交付的证据 | 量化退出标准（示例） | 失败处理 |
|---|---|---|---|
| G0（M0） | 技术选型 ADR、契约冻结、fake E2E、trace harness、依赖锁 | 契约测试 100% 通过；非法配置 100% 快速失败；可控 Worker 能复现 3 种到达顺序；AGENTS 命令表已填 | 不进入 M1；先修契约/选型 |
| G1（M1） | 50 篇真实入库、检索/证据/引用句 E2E、gold set v0 | Recall@20 ≥ 基线；证据定位有效率 ≥95%；无依据引用句 95% 上界 <5%；关键词 TTFF p95 ≤8s | 不进入 M2；先修解析/证据/质量 |
| G2（M2） | 5 库（含慢库/失败库）、SSE、快照、去重、预算 | 慢库不阻塞快库（AT-STR-001）；p95 TTFF 在 SLO 内；同 DOI 单结果；重放一致；成本 ≤上限 | 不进入 M3；先修流式/评分/预算 |
| G3（M3） | 全文插入、已有引用复用、数字编号联动、docx 导出 | 正文—文末双向一致；复杂 docx 零静默损坏；重复导出编号一致；锚点失败有明确错误 | 不进入 M4；先修 Word/编号 |
| G4（M4） | 多租户、权限、删除、负载、故障恢复、成本报告 | 跨租户/越权/注入 0 高危；20 并发不崩；恢复后快照不变；单查询成本 ≤预算 | 不发布；先修安全/运维 |

**关键改动**：

- 每个门禁必须有“证据包”：测试报告（通过/失败/跳过数）、指标（含 CI）、失败样本、已知限制、签字人。
- 性能/质量门禁必须与**版本化基线**比较，而不是与“上一次演示”比较。
- 安全/隐私从 G0 起持续，不等到 G4；G4 只是最终验证。
- 门禁失败时，允许“缩小范围 + 明确剩余”，但不得把部分功能改名成完整系统（FND-031）。

### 5.5 Agent 实施可行性评估（独立于 AGENTS 审查）

**结论 [推断]**：这套规格**可以**由 coding agent 分片实现，但**不可以**按当前任务粒度一次性实现；M0 可行，M1 可行但质量不可证，M2–M3 高风险，M4 需要人类运维/安全参与。

| 能力 | 可行性 | 原因 | 缓解 |
|---|---|---|---|
| 仓库骨架、契约 Schema、Pydantic/TS 生成、CI | 高 | 确定性、可测试 | T01 + 选型 ADR |
| PDF 解析/索引 | 中 | 版式/扫描/坐标不确定性高 | E9 bake-off + golden PDFs |
| 混合检索/预算 | 中高 | 算法明确，但 BM25/向量/参数需调 | E1/E4 + 合成库 |
| 证据核验 | 低–中 | 语义判断 + 逐字定位 + 模型不确定性 | span 选择 + gold set + 两段式核验 |
| 流式协调/去重/快照 | 高 | 状态机/事件契约明确 | 可控 Worker + 事件重放 |
| 评分/校准 | 低–中 | 目标标签未定义、标注成本高 | 先 bootstrap + 后校准 |
| Word/OOXML 导出 | 低 | 高保真编辑复杂 | E10 + 只导出变更清单的 fallback |
| 安全/多租户 | 中 | 需要威胁模型/基础设施 | 选型 + AT-SEC + 红队 |
| 性能调优 | 低–中 | 依赖真实模型/负载 | E2–E6 + SLO |

**Agent 会在哪里失败 [推断]**：

- **上下文超载**：1704 行 SPEC + 410 行 AGENTS + 代码/测试输出，coding agent 容易只记住局部，忘记不变量；需要“任务卡”只读相关 50–100 行，而不是每次通读全文。
- **产品决策缺位**：`display_score` 目标、文献类型资格、成本预算、认证方式，这些不是 coding agent 能自行决定的；它会在实现中“猜一个”，然后测试围绕猜测写。
- **长任务无反馈**：T03/T08 这类 2–4 周任务，agent 容易在错误方向上走很远；需要 1–2 天的垂直切片 + 每个切片可运行。
- **测试自欺**：agent 会倾向写“能通过”的测试（fake model、字段非空、HTTP 200）；需要人类预写验收标准、gold set、反例测试。
- **外部依赖/许可证**：解析器、docx 库、CSL、认证、云服务的选择涉及许可证/合规，agent 不能独自决定。

**建议的任务粒度**：

- 每个任务 ≤1–2 人日，产出“可运行切片 + 测试 + 指标 + 一句风险”。
- 每个任务只读 SPEC 的一个小节 + 相关契约 + 1 个 AT；任务卡写明“不要读全文”。
- 每个任务必须有“失败反例”测试，而不仅是正向测试。
- 每 3–5 个任务做一次集成/性能/安全回归，不要等到 T11。

**人类必须保留的决策点**：技术选型（P0-03）、评分目标（P1-05）、成本预算（P0-05）、认证/租户（P1-07）、Word 保真降级策略（P1-08）、是否采用替代架构（§6）、是否接受部分覆盖/发布（门禁）。

**工作量 [假设]**：2–3 名工程师约 19–25 人周；单个 coding agent 连续执行约 3–6 个月，且需要人类定期裁决上述决策。这个估算必须用 T01.5/E9/E10 的 spike 校准，不是承诺。

## 6. 替代架构与采用条件（均为提案，不是擅自变更需求）

> 以下提案会触及 ADR-002/003/007 或 INV-02/06；按 FND-003 与 AGENTS §4.11，必须先取得用户明确同意，再改 SPEC/ADR，再改代码，最后补 `T-INV-*`。本报告不替用户做决定。

| 替代 | 替代什么 | 相对当前方案的主要收益 | 主要代价 | 采用条件（摘要） |
|---|---|---|---|---|
| A1 共享验证池 | 每库全流程 Worker 的高成本阶段 | 全局限流、批处理、吞吐/成本、快库优先 | 多一个服务、公平调度复杂、边界争议 | ≥3 库或 ≥10 QPS；E4 通过 |
| A2 确定性 Planner + 可选 Agent | 始终由单 Agent 规划 | 首结果更快、可复现、成本低 | 词典维护、弱项灵活性 | 100 query 上达到 Agent 95% 召回；E1/E2 |
| A3 证据优先分组 | 统一 0–100 分作为唯一排序 | 消除跨库校准负担、减少误读 | 失去全局排序、与 INV-02 冲突 | 用户研究通过且用户同意改需求 |
| A4 Canonical Work Entity | 单层 Paper/Recommendation | 跨库/版本合并、证据可审计 | Schema/迁移复杂 | P0-01 修复时采用 |
| A5 两段式核验 | LLM 全量核验 | LLM 调用 -40–70%、成本/延迟下降 | 假阴性、阈值调参、关系粒度 | E3 通过；否则不全量替换 |

### A1：共享验证池（替代“每库全流程 Worker”中的高成本阶段）

**改什么**：保留每库检索 Worker；把 rerank、证据读取、关系核验抽成按 query 分区的共享池。检索 Worker 产出候选到优先队列；共享池按 query 公平调度、按 batch 调用；结果逐条回协调器。

**收益**：

- 全局 token/QPS 控制，减少 429 与重试雪崩；
- reranker/LLM 批处理，吞吐提升、单位成本下降；
- 快库高价值候选可以优先，不被慢库长尾挤占；
- 仍然满足 INV-01：没有“等全部 Worker”的屏障，单条结果完成即发布。

**代价**：

- 多一个共享服务；跨 query 公平调度与故障隔离复杂；
- 可能违反 FND-043 的“Worker 只访问本库”字面边界（用“服务”而非“Worker”可规避）；
- 需要新的指标：队列等待、每 query 配额、公平性比值。

**采用条件**：

- ≥3 个库，或 ≥10 QPS，或 provider 429 率 >1%；
- E4 实验显示：共享池在相同 p95 TTFF 下吞吐 +30%，或相同吞吐下 p95 TTFF -20%；
- 公平性：最慢 query / 最快 query 的 p95 TTFF 比值 <2；
- 若实验不满足，保留每库 Worker + 全局 token bucket（A1-lite），成本更低。

**回滚**：共享池开关关闭后，回退到每库 Worker 本地 rerank/verify；事件契约不变。

### A2：确定性 Planner + 可选 Agent Router（替代“始终单 Agent 规划”）

**改什么**：默认使用确定性查询规划器（规范化、术语保留、同义词/缩写扩展、库路由规则、预算策略）；只有“输入歧义/新主题/用户明确要求探索”时调用 LLM Agent 生成 `SearchPlan`。Agent 输出仍受确定性校验器与预算引擎约束。

**收益**：

- 关键词/摘要模式首结果更快（少一次 1–5s 的规划 LLM 调用）；
- 规划可复现、可回归测试；成本更低；
- Agent 仍保留在真正需要探索的场景。

**代价**：

- 确定性规划器需要维护同义词/缩写/物种/基因词典；
- 对全新主题可能不如 Agent 灵活；
- 需要两套路径的评测与监控。

**采用条件**：

- 在 100 条分层查询上，确定性 Planner 的 Recall@20 ≥ Agent 的 95%，且 p95 规划延迟 ≤ 20%；
- Agent 仅在“规划置信度低”或“用户要求扩查”时触发；触发率 ≤20%；
- 若 Agent 在 >20% 查询上显著提升 Recall（≥5 点），保留 Agent 优先。

**与当前方案相比**：这是对 FND-021/ADR-002 的挑战；如果用户坚持“Agent 必须负责查询规划”，则只做“确定性校验器 + 预算钳制”，不改规划主体。

### A3：证据优先分组（替代“统一 0–100 分”作为唯一排序）

**改什么**：UI 先按关系/证据状态分组（`support`、`complement`、`contrast`、`related-but-insufficient`），组内用简单相关性排序；不再把跨库分数作为唯一排序与展示核心。

**收益**：

- 消除跨库校准的标注负担与“伪精确”风险；
- 用户先看“证据能支持什么”，符合产品核心价值；
- 减少“分数=概率”的误读。

**代价**：

- 失去一个全局排序，用户可能更难决定“先看哪条”；
- 与 INV-02/SCR-001～009 冲突；需要改 SPEC/ADR 和 UI；
- 需要用户研究证明分组更有效。

**采用条件**：

- E8 用户研究：分组 UI 的选择时间 -20%，误解率 -50%，且不增加漏选；
- 用户明确同意修改“统一展示分”的需求；否则只作为可选视图，不替代主排序。

### A4：Canonical Work Entity + Source Records（修复 P0-01 的数据架构）

**改什么**：引入 `work`（知识对象）与 `paper_source`（库内记录）两层；`result_id` 绑定 `work`；`Evidence` 绑定 `paper_source`；`Recommendation` 聚合 `work` + `paper_sources[]`。

**收益**：跨库同 DOI/预印本/版本可合并；证据溯源完整；快照可审计；为未来“同一论文多版本”打基础。

**代价**：Schema/迁移/查询复杂度上升；需要定义 work 匹配规则（DOI、标题+作者+年份、预印本关系）；旧数据迁移。

**采用条件**：P0-01 修复时采用；如果只想最小改动，至少加 `paper_sources[]`，不引入完整 work 表。

### A5：两段式核验（NLI/交叉编码器门控 + LLM 裁决）

**改什么**：先用便宜的 NLI/交叉编码器对“claim-evidence”打分，低于阈值直接 `insufficient`，高于阈值直接 `support/complement/contrast`（需校准），只有中间带交给 LLM。

**收益**：LLM 调用减少 40–70%，成本/延迟下降；NLI 模型可本地部署，隐私更好。

**代价**：门控阈值会引入假阴性；需要标注集调参；NLI 对科学术语/长句可能不准；关系类型（support/complement/contrast）比 NLI 三分类更细。

**采用条件**：

- E3 实验：在 gold set 上，门控减少 LLM 调用 ≥40%，证据召回损失 ≤2 点，误拒率 ≤5%；
- 若达不到，保留 LLM 全量核验，或只对“明显不相关”做门控。

## 7. Pareto 基准比较方案（避免伪最优）

### 7.1 原则

1. **先约束，后 Pareto**：证据/安全/隐私是硬约束（不满足直接淘汰），不参与加权；在可行配置中比较质量、延迟、吞吐、成本、复杂度、可实施性。
2. **不把多目标压成一个加权分**：加权和会掩盖“质量高但成本爆炸”或“快但证据差”；用 Pareto 前沿 + 约束筛选。
3. **不声称全局最优**：只报告“在已评估配置集合中的非支配集”；明确设计空间、数据、版本、预算。
4. **配对比较**：同一 query、同一 gold label、同一硬件/模型版本下比较；用配对 bootstrap/Wilcoxon，报告 95% CI。
5. **长尾优先**：报告 p50/p95/p99，不只均值；首结果和最终结果分开；按输入模式/库数/主题分桶。
6. **成本全口径**：token、rerank 调用、embedding、索引构建摊销、GPU 小时、存储、运维人力；不要只算 API 账单。
7. **复杂度可度量**：服务数、关键路径同步跳数、配置项数量、状态机数量、依赖数量、构建时间、故障注入通过率。
8. **可实施性可度量**：到 M1/M2 的人日、测试编写时间、flaky rate、 onboarding 时间；用 spike 估算，不拍脑袋。
9. **安全可度量**：AT-SEC 通过率、跨租户/注入/恶意文件测试的高危发现数；安全是约束，不是“加分项”。
10. **预先注册**：实验前写假设、主指标、停止规则、最小可检测效应；避免事后挑指标。

### 7.2 目标与指标

| 维度 | 指标 | 测量方式 | 方向 |
|---|---|---|---|
| 质量 | Recall@20、nDCG@10、MRR、证据 precision/recall、引用句采纳率 | gold set + 人工/LLM 辅助评审 | 最大化 |
| 召回 | 分阶段 Recall（关键词/向量/融合/重排/核验）、端到端 Recall@K | 标注 qrels，定位首次丢失阶段 | 最大化 |
| 首结果延迟 | TTFF（首条 eligible）、TTFC（首条 citable） | 事件时间戳，p50/p95/p99 | 最小化 |
| 最终延迟 | 创建→final snapshot | 事件时间戳，p50/p95 | 最小化 |
| 吞吐 | 在 SLO 下的 queries/min、并发用户数 | 负载测试 | 最大化 |
| 成本 | USD/query、token/query、rerank calls/query、索引摊销 | 账单 + 计数器 | 最小化 |
| 复杂度 | 服务数、关键路径跳数、配置项、状态机、依赖数 | 架构清单 + 代码扫描 | 最小化 |
| 安全 | AT-SEC 通过率、高危发现数、注入成功率 | 威胁模型测试 | 约束 |
| 可实施性 | 到 M1/M2 人日、测试 flaky rate、构建时间 | 任务日志 + CI | 最小化 |

### 7.3 设计空间（至少比较这些配置）

| 维度 | 配置 |
|---|---|
| 检索 | BM25 only；dense only；hybrid RRF k=60；hybrid RRF k tuned；weighted fusion |
| 重排 | none；cross-encoder；LLM listwise；cross-encoder + LLM fallback |
| 核验 | LLM 全量；NLI 门控 + LLM；cross-encoder 门控 + LLM；规则 + LLM |
| 编排 | 每库 Worker；共享验证池；每库 Worker + 全局 token bucket |
| 预算 | 全局 120；per-claim 10/20/40 + 总上限；动态 TopN |
| 评分 | bootstrap sigmoid；global calibration；source calibration；uncalibrated grouping |
| 流式 | 逐条；micro-batch 4/250ms；micro-batch 8/500ms |
| UI | 统一分数；证据优先分组；分数 + 分组混合 |

### 7.4 统计与报告

- 样本量：每个主实验至少 100 条 query（关键词/摘要/全文分层）；每条 query 有 10–50 个候选；gold set 200–300 条 claim-evidence 对。
- 统计：配对 bootstrap 10,000 次；Wilcoxon signed-rank；多重比较用 Holm/BH；报告效应量与 95% CI。
- 失败：所有超时、429、解析失败、空结果都计入分母；不得只报告成功 query。
- 报告：Pareto 前沿图（质量 vs p95 TTFF vs 成本），表格列出非支配配置；每个配置标注版本/硬件/模型；附“被淘汰原因”。
- 决策：先满足硬约束（证据/安全/SLO），再在 Pareto 前沿上按产品偏好选；如果两个配置互不支配，交给用户/产品决策，不偷偷加权。

### 7.5 避免伪最优的检查清单

- [ ] 是否在同一 test set 上调参？→ 用 held-out topics / nested CV。
- [ ] 是否只报告均值？→ 报告 p50/p95/p99 + CI。
- [ ] 是否忽略成本？→ 全口径成本。
- [ ] 是否忽略失败/超时？→ 计入分母。
- [ ] 是否用单一 LLM judge？→ 人工抽样校准，检查 position/verbosity/self-enhancement bias（[LLM-as-judge](https://arxiv.org/abs/2306.05685)）。
- [ ] 是否把 50 篇语料当唯一证据？→ 补充公开基准（BEIR/MTEB）做组件级，自建领域金标做端到端。
- [ ] 是否把“统计显著”当“产品重要”？→ 预设最小可检测效应。
- [ ] 是否把“当前最优”说成“全局最优”？→ 明确设计空间与未评估区域。
- [ ] 是否只测快库？→ 慢库/失败库/429/超时注入。
- [ ] 是否只测单租户？→ 跨租户/权限撤销/注入。

### 7.6 基准实验矩阵

| ID | 问题 | 设计 | 主指标 | 通过标准（示例） |
|---|---|---|---|---|
| E0 | 测量本身可信吗 | 可控 Worker + 固定事件 trace + 注入时钟，100 次重放 | 重放一致性、p95 稳定性 | 100 次最终快照一致；p95 波动 <5% |
| E1 | 混合检索是否值得 | BM25 vs dense vs RRF k=60 vs tuned k；50 篇 + 100 query；BEIR 组件级补充 | Recall@20、nDCG@10、延迟 | hybrid Recall@20 ≥ max(BM25,dense)+3 点，95% CI 下限 >0；p95 ≤500ms |
| E2 | 重排是否值得 | none vs cross-encoder vs LLM listwise；batch 1/4/8 | nDCG@10、证据 precision、p95、成本 | cross-encoder +3 点，p95 +≤1.5s，成本 +≤$0.01/query；否则不重排 |
| E3 | 两段式核验是否安全 | LLM 全量 vs NLI 门控阈值 0.3/0.5/0.7 | 证据召回、误拒率、LLM 调用数、成本 | 调用 -40%，召回损失 ≤2 点，误拒 ≤5%；否则全量 |
| E4 | 共享池是否更好 | 每库 Worker vs 共享池；并发 4/8/16 | p95 TTFF、吞吐、公平性、成本 | 同 TTFF 下吞吐 +30%，公平比值 <2；否则不换 |
| E5 | 分数是否可校准 | bootstrap vs global calibration vs source calibration；relevance vs citation utility 标签 | Brier、ECE、nDCG、误解率 | Brier/ECE 各降 ≥0.05；否则保持 bootstrap 并标注 |
| E6 | 微批是否伤害首结果 | 逐条 vs 4/250ms vs 8/500ms | TTFF p95、吞吐、事件数 | 吞吐 +20%，TTFF p95 +≤10%；否则逐条 |
| E7 | 全文预算怎么分 | 全局 120 vs per-claim 10/20/40 + 总上限 | 每 claim Recall、总成本、p95 | per-claim 20 达到全局 120 的 90% 召回，成本 ≤50%；否则调整 |
| E8 | 统一分数是否必要 | 统一分 vs 证据分组；用户 10–20 人 | 选择时间、信任、误解率、漏选 | 分组 -20% 时间、-50% 误解、漏选不增；否则保留分数 |
| E9 | 解析器选谁 | PyMuPDF/GROBID/MinerU/Docling；10 篇代表性 PDF | 阅读顺序、章节、坐标、表格、速度 | 章节/顺序 ≥95%；否则加 fallback/OCR |
| E10 | Word 导出怎么保真 | python-docx/docx4j/LibreOffice UNO；复杂 docx | round-trip diff、域/批注/修订保留、编号 | 零静默损坏；不支持结构明确报告；否则只导出变更清单 |
